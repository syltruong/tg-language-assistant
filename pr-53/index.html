1. Background

1.1 The system, for newcomers

This is a Telegram bot that helps someone learning a new language — say, an English speaker learning French — while they're mid-conversation with a native speaker. The user configures a Language Pair: a base language (always English, the language they're comfortable in) and a target language (French, Malay, or Chinese — the one they're learning). Every message they forward to the bot gets classified against that pair and then acted on — translated, corrected, explained, and so on.

The component responsible for that classification is the Message Gateway (bot/gateway.py) — the single entry point for every incoming Telegram Update. Before this PR, its job was:

  1. Ask the Authorizer whether this user is allowed to use the bot.
  2. Pull the raw text out of the Telegram message, reject if empty, too long, or emoji-only.
  3. Run a language detector over the text to get an ISO code ("en", "fr", …).
  4. Compare that ISO code against the user's Language Pair to assign a Language Role: TARGET if it matches the target language, BASE if it matches the base language.
  5. If it matches neither, raise UnsupportedLanguageError.

The language detector itself was lingua, a fast, purely statistical, offline library — no network call, no LLM. Good for speed, but it can misfire on short or ambiguous text (a two-word message doesn't give a statistical model much to work with).

Separately, the bot already had an LLMClient abstraction (bot/llm_interface.py) wrapped in a small LangGraph graph purely so that calls could be traced in LangSmith — a single node, call_llm, that reads a system_prompt/user_prompt pair out of graph state and writes the completion back as output. That graph had nothing to do with language detection; it existed only as a tracing seam around whichever LLM call needed it (translation, correction, etc.).

Finally, every error the bot can show a user is a small typed exception (UserFacingError subclasses in bot/errors.py) resolved to display text through a Localizer, which looks the exception's class up in a per-locale string catalog (bot/config/messages.py). This indirection is what lets the same crash type read differently depending on the user's locale, and it's also where this PR's bug was hiding.

1.2 What was actually broken

Before this PR, UnsupportedLanguageError was not registered in the message catalog at all — only MsgUnknownLanguage, a separate, unused MsgKey with a hardcoded "French or English" message, existed nearby. So when the exception fired, MessageTrigger caught it and tried to render it: 

self._localizer.t(type(exc), session.base_language)

Localizer.t() looks the key up with catalog.get(key, CATALOGS[DEFAULT_LOCALE][key]) — and since UnsupportedLanguageError wasn't a key in either the requested locale's catalog or the English fallback catalog, that fallback lookup itself raised KeyError. That KeyError happened inside the except UserFacingError block that was supposed to be sending the user a friendly reply — so it propagated straight out of MessageTrigger.handle, unhandled. The user sent a message in an unsupported language and got nothing back at all: a silent failure, diagnosable only by grepping the bot's logs for a stack trace.

Worth noting This is the classic "the error handler has its own bug" trap: the exception path is the one path that's hardest to exercise in manual testing, because triggering it usually means the feature is already broken in some other way too.

2. Intuition

This PR fixes two things, and they turn out to be entangled: the crash above, and the accuracy of the underlying detection that was triggering it more often than it should.

2.1 Fix #1 — give UnsupportedLanguageError a real message

The straightforward half of the fix: register the exception in the catalog, with a template that takes the base and target language codes as placeholders, and thread those codes through when the exception is constructed and when it's rendered.

Hola mundo
✂ connection interrupted — no reply, nothing in the chat
Before: an unsupported-language message in the EN/FR pair vanished.
Hola mundo
Sorry, I couldn't tell if that was written in en or fr. Please send text in one of those languages.
After: the same message now gets an actual reply, with the pair's two languages filled in.
A subtlety The final error message interpolates the raw ISO codes (en, fr) rather than display names ("English", "French") — that's what the new catalog template (bot/config/messages.py) literally does. Contrast this with the LLM fallback prompt below, which does use LANGUAGE_NAMES to build a human-readable prompt. Two different call sites, two different choices about which language label to use.

2.2 Fix #2 — don't give up after one detector's guess

The second half addresses why the error fires in the first place. lingua is a fast, offline, statistical detector — reliable on longer text, but it can misclassify short or ambiguous messages. Previously, one wrong guess from lingua was final: if it didn't match the base or target language, the user got rejected outright (crash aside).

Now there's a second opinion. The gateway no longer talks to a raw LanguageDetector directly — it talks to a new LanguageClassifier abstraction, whose one concrete implementation, GraphLanguageClassifier, runs a two-node LangGraph graph: try the deterministic detector first, and only if that guess lands outside the user's language pair, ask the LLM to break the tie before finally giving up.

entry detect_deterministic
runs lingua on the text
↓
role matches base or target?
yes ↓
END
return detector's ISO + role
no ↓
call_llm
shared node from llm_interface.py
↓
END
parse LLM's reply, or raise
The two-node graph inside GraphLanguageClassifier. The conditional edge only fires the LLM node when the cheap deterministic path fails.

Walking through the exact example from this PR's own test suite, for the pair base=en, target=fr:

StepWhat happens
User sends"Bonjour"
detect_deterministiclingua misfires and returns "es" (Spanish) — matches neither en nor fr
Routing decisionrole is None → build a fallback prompt and route to call_llm
Fallback prompt (built from LANGUAGE_NAMES)"Is the following text written in English or French? Reply with only the ISO code 'en' or 'fr', or the word 'none' if it is neither."
LLM replies"fr"
Result("fr", LanguageRole.TARGET) — message is correctly classified after all

And the failure case — same pair, user sends "Hola", detector again says "es", but this time the LLM also replies "none". Now GraphLanguageClassifier.classify() raises UnsupportedLanguageError(base="en", target="fr") — which, thanks to Fix #1, now renders as a real reply instead of vanishing.

Why reuse call_llm instead of writing a new node? The completion graph in llm_interface.py was already a single node that reads system_prompt/user_prompt from state and writes output back. That shape is generic enough to drop into any graph with matching state keys — so this PR pulls the node-building logic out into build_call_llm_node() and reuses it verbatim as the second node of the new language-detection graph. One function, two graphs.

3. Code walkthrough

3.1 bot/errors.py and bot/config/messages.py — giving the error a voice

UserFacingError itself is untouched — it already stored arbitrary **format_kwargs on construction (that plumbing pre-dates this PR and was simply unused for this exception). What's new is the catalog entry that actually consumes those kwargs:

bot/config/messages.py
UnsupportedLanguageError: (
    "Sorry, I couldn't tell if that was written in {base} or {target}."
    " Please send text in one of those languages."
),

Localizer.t(key, locale, **kwargs) does a plain str.format(**kwargs) against that template, so base and target need to be supplied wherever this error is raised.

3.2 bot/triggers/message.py — actually passing those kwargs through

The other half of Fix #1. MessageTrigger.handle() used to call t(type(exc), session.base_language) with no kwargs at all; now it forwards whatever the exception was constructed with: 

self._localizer.t(type(exc), session.base_language, **exc.format_kwargs)

This is a generic fix, not one special-cased to UnsupportedLanguageError — any future UserFacingError subclass that's raised with keyword arguments and has a matching {placeholder} in its catalog template will now render correctly too.

3.3 bot/gateway.py — the classification step becomes pluggable and async

MessageGateway no longer owns the base/target comparison logic inline. It delegates to a new LanguageClassifier protocol: 

@runtime_checkable
class LanguageClassifier(Protocol):
    async def classify(self, text: str, language_pair: LanguagePair) -> tuple[str, LanguageRole]: ...

and its constructor swaps a language_detector: LanguageDetector dependency for language_classifier: LanguageClassifier. Because classification may now involve an LLM call, MessageGateway.process() itself becomes async def — a ripple that touches every caller and every test (see 3.6). The old LanguageDetector protocol and the lingua-backed LinguaLanguageDetector stick around unchanged; they're just wrapped now instead of called directly.

3.4 bot/llm_interface.py — extracting a reusable graph node

The single-node completion graph's node function is pulled out of its closure and exposed as a standalone factory: 

def build_call_llm_node(inner: LLMClient):
    async def call_llm(state: dict) -> dict:
        completion = await inner.complete(state["system_prompt"], state["user_prompt"])
        return {**state, "output": completion.text}
    return call_llm

def _build_completion_graph(inner: LLMClient):
    graph = StateGraph(AgentState)
    graph.add_node("call_llm", build_call_llm_node(inner))
    ...

The node only reads/writes system_prompt, user_prompt, and output — it doesn't care what else lives in the state dict — which is precisely what makes it safe to reuse inside LanguageDetectionState, a differently-shaped TypedDict, in the next file.

3.5 bot/language_detection.py — the new module, in full

This is the new file that ties the deterministic detector and the LLM together. Its pieces, in the order they execute:

  • LanguageDetectionState — the graph's state shape: input (text, base, target), scratch fields for the LLM path (system_prompt, user_prompt, output), and the result (detected_language, role).
  • _classify(iso_code, base, target) — the exact comparison that used to live inline in MessageGateway.process(), now shared by both the deterministic node and the LLM-fallback parsing step.
  • _build_fallback_prompt() — builds the system prompt shown in the walkthrough above, using LANGUAGE_NAMES for human-readable names.
  • _build_graph() — wires the two nodes and the conditional edge described in Intuition §2.2.
  • GraphLanguageClassifier — the public class, implementing LanguageClassifier.classify() by invoking the compiled graph and interpreting its final state.
  • FakeLanguageClassifier — a test double that always returns a fixed (iso_code, role) pair, replacing the old FakeLanguageDetector at most call sites.

The raise site for the "still unsupported after asking the LLM" case is where the two fixes finally meet:

fallback_iso = result["output"].strip().lower()
fallback_role = _classify(fallback_iso, language_pair.base, language_pair.target)
if fallback_role is None:
    raise UnsupportedLanguageError(base=language_pair.base, target=language_pair.target)

3.6 bot/main.py — wiring it together

llm = LangGraphLLMClient(inner=OpenAILLMClient(api_key=OPENAI_API_KEY, model=MODEL_NAME))
language_classifier = GraphLanguageClassifier(
    language_detector=LinguaLanguageDetector(), llm_client=llm
)
gateway = MessageGateway(authorizer=authorizer, language_classifier=language_classifier)

Note that llm — the same LangGraphLLMClient used for translations and corrections elsewhere — is handed straight to GraphLanguageClassifier too. There's no separate model or client for language detection; it's the same completion path, just invoked with a different prompt.

3.7 Tests — following the ripple

Because MessageGateway.process() is now a coroutine, every existing test in bot/test_gateway.py and bot/triggers/test_message.py gained async def / await. FakeLanguageDetector is replaced by FakeLanguageClassifier(iso_code, role) at gateway/trigger call sites (the raw detector fake still exists and is reused directly inside the new bot/test_language_detection.py, since GraphLanguageClassifier still needs one to plug into its graph).

The new bot/test_language_detection.py is where the LangGraph routing itself is pinned down — including a deliberately hostile _ExplodingLLMClient whose complete() always raises AssertionError, used to prove the LLM node is never reached when the deterministic detector already matched: 

class _ExplodingLLMClient:
    """An LLMClient that fails the test if it's ever called."""
    async def complete(self, system_prompt, user_prompt, *, metadata=None):
        raise AssertionError("LLM fallback should not be called when the deterministic detector already matched")

And bot/triggers/test_message.py gets the regression test for the original bug report, using a _RaisingClassifier that always raises UnsupportedLanguageError, asserting the user gets a real reply mentioning both language codes instead of the handler silently dying: 

async def test_user_receives_a_reply_instead_of_a_silent_failure(self):
    trigger, runner, _ = _make_trigger(language_classifier=_RaisingClassifier())
    update = make_update(text="Hola mundo", user_id=1)
    context = make_context()

    await trigger.handle(update, context)

    update.message.reply_text.assert_awaited_once()
    reply_text = update.message.reply_text.await_args.args[0]
    assert "en" in reply_text
    assert "fr" in reply_text
    assert runner.last_action is None
