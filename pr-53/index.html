Fixing a silent failure: language detection gets an LLM safety net

How tg-language-assistant stopped swallowing errors for unsupported languages, and taught its language detector to ask an LLM when it's unsure.

Background

This bot sits on top of Telegram and helps a user practise a "target" language against a "base" language they already know — think an English speaker (base = en) drilling French (target = fr). Skip ahead to the narrow background if you already know how a message becomes a translation.

Deep background: how a message becomes a reply

Every incoming Telegram message flows through the same short pipeline, and each stage has one job:

Telegram
Update
→
MessageTrigger
→
MessageGateway
→
AnchorMessage
→
ActionRunner
(translate)

MessageTrigger is the entry point registered with python-telegram-bot; MessageGateway does the validation and classification that turns a raw Update into a typed, trustworthy AnchorMessage.

MessageGateway.process() runs a chain of checks, each of which can bail out with its own exception type: is the user authorized (UnauthorizedError)? Does the update actually contain text (MessageHasNoTextError)? Is it under 500 characters (TextTooLongError)? Does it contain actual letters, as opposed to only emoji (TextHasNoWrittenContentError)? And finally: what language is it in, and does that language belong to the user's chosen pair (UnsupportedLanguageError)?

All of these exceptions share a common base, UserFacingError, defined in bot/errors.py:

class UserFacingError(Exception):
    def __init__(self, *args, **format_kwargs):
        super().__init__(*args)
        self.format_kwargs = format_kwargs

The idea is elegant: an error class doubles as a lookup key into a message catalog (bot/config/messages.py), and any keyword arguments passed when the error is raised are stashed away so they can later be substituted into the message template — a small, homegrown i18n system. MessageTrigger.handle() catches any UserFacingError and asks the Localizer to render the matching string in the user's base language.

Narrow background: detecting the language, before this change

Before this PR, language detection was a single synchronous call embedded directly inside MessageGateway.process(). A LanguageDetector protocol had one method, detect(text) -> str (an ISO code), implemented by LinguaLanguageDetector — a wrapper around the Lingua statistical language-detection library. The gateway then compared that ISO code against the user's base/target pair inline:

detected_iso = self._language_detector.detect(text)

if detected_iso == language_pair.target:
    role = LanguageRole.TARGET
elif detected_iso == language_pair.base:
    role = LanguageRole.BASE
else:
    raise UnsupportedLanguageError()

Two things about this code turn out to matter a great deal. First, statistical detectors like Lingua are unreliable on very short strings — a two-word message like "Bonjour" doesn't give it much signal, and it can easily guess Spanish or Italian instead of French. Second, look closely at that final line: raise UnsupportedLanguageError() is called with no keyword arguments at all. Whatever ISO codes were involved are lost the instant the exception is raised.

The bug hiding here Even though UserFacingError supports format_kwargs, and messages.py supports templated strings like "...in {base} or {target}", UnsupportedLanguageError wasn't in the message catalog at all before this PR, and MessageTrigger never forwarded exc.format_kwargs into the render call anyway. Two missing pieces, one silent failure — explained fully in Intuition below.

Intuition

This PR fixes two problems that turn out to share a root cause: the bot gave up too easily when it wasn't sure what language a message was in. One bug is about what happens after giving up (the user hears nothing); the other is about how quickly the bot gives up in the first place (before even asking an LLM to double-check). Let's take them in order.

Bug #1: the silent failure

Picture a user with the pair en/fr who, by mistake, sends "Hola mundo" (Spanish). The detector correctly reports es, which matches neither en nor fr, so the gateway raises UnsupportedLanguageError(). MessageTrigger catches it and tries to look up a friendly message:

self._localizer.t(type(exc), session.base_language)

Under the hood, Localizer.t() does CATALOGS[locale][key], falling back to the English catalog. But UnsupportedLanguageError was never added as a key to that catalog — so this lookup itself raises a plain KeyError, inside the exception handler that was supposed to apologize to the user. That KeyError isn't a UserFacingError, so nothing catches it gracefully; python-telegram-bot's own error handling swallows it, and the user simply... never gets a reply.

Before the fix
Hola mundo
(the bot never replies — a KeyError was thrown while trying to apologize)

The fix is two small, precise additions. First, register the error in the catalog with a template that actually uses the base/target placeholders:

UnsupportedLanguageError: (
    "Sorry, I couldn't tell if that was written in {base} or {target}."
    " Please send text in one of those languages."
),

Second, make sure those placeholders actually get filled in, by forwarding exc.format_kwargs from wherever the error is caught:

self._localizer.t(type(exc), session.base_language, **exc.format_kwargs)

Which means UnsupportedLanguageError now needs to be raised with base= and target= keyword arguments wherever it's thrown — which brings us to the second half of this PR.

After the fix
Hola mundo
Sorry, I couldn't tell if that was written in en or fr. Please send text in one of those languages.

Bug #2: giving up too early

Now picture a trickier case: the same en/fr user sends "Bonjour" — genuinely French, and genuinely a member of their language pair. But "Bonjour" is a single short word, and Lingua's statistical model, starved of signal, might report es anyway. Under the old code, that's an immediate UnsupportedLanguageError — a real French sentence gets rejected because a fast, cheap, offline detector had a bad guess.

The PR's answer: don't treat the deterministic detector's answer as final if it doesn't match either language in the pair. Instead, ask the LLM to arbitrate, since the LLM is far better at classifying short, ambiguous text than a purely statistical model — it just costs a network round-trip, so it's worth reserving for the ambiguous cases only.

text: "Bonjour"
→
detect_deterministic
(Lingua)
iso = "es" — matches neither en nor fr
→
call_llm
"is this en or fr, or neither?"
→
"fr" → role = TARGET

The new GraphLanguageClassifier: a deterministic first pass, with a conditional edge to an LLM fallback only when the first pass is inconclusive for this user's language pair.

And if the LLM also can't place the text in either language — e.g. the user really did send Spanish — that's when UnsupportedLanguageError is finally raised, and now it's raised with the actual codes attached:

raise UnsupportedLanguageError(base=language_pair.base, target=language_pair.target)

This closes the loop with Bug #1: the error is now always raised with the base/target keyword arguments the catalog template expects, so the "sorry, couldn't tell" message renders correctly no matter which stage of detection triggered it.

Why a graph, and not just an if/else? The bot already used LangGraph to wrap its LLM calls for tracing (via LangSmith) in llm_interface.py. Modelling detection as a two-node graph (detect_deterministic → conditional edge → call_llm) means the LLM fallback call gets the same tracing/observability treatment as every other LLM call in the system, essentially for free — it reuses the exact node-building function the completion graph already relies on.

Code walkthrough

The change touches five production files. Rather than walk them in diff order, it's clearer to follow the shape of the new abstraction: a new module is introduced, an old collaborator is replaced with it, a small piece of shared plumbing is extracted to support it, and then the wiring and tests catch up.

1. The new classifier: bot/language_detection.py

This is the heart of the PR: a brand-new module defining the two-node LangGraph graph described above, wrapped in a class that matches a small protocol.

bot/language_detection.py 
class LanguageDetectionState(TypedDict):
    text: str
    base: str
    target: str
    detected_language: str
    role: str | None
    system_prompt: str
    user_prompt: str
    output: str

This is the graph's shared state — every node reads and writes a slice of it. Note it's a superset of the AgentState used by the existing completion graph in llm_interface.py (which only needs system_prompt/user_prompt/output); that overlap is exactly what lets the two graphs share a node implementation.

The helper functions are small and purposeful:

  • _classify(iso_code, base, target) — the exact same three-way comparison that used to live inline in MessageGateway.process(), now extracted so both the deterministic node and the LLM-fallback path can reuse it.
  • _build_fallback_prompt(text, base, target) — builds the system prompt sent to the LLM, e.g. "Is the following text written in English or French? Reply with only the ISO code 'en' or 'fr', or the word 'none' if it is neither." using the friendly names from LANGUAGE_NAMES rather than raw ISO codes.

_build_graph() wires the two nodes together:

graph = StateGraph(LanguageDetectionState)
graph.add_node("detect_deterministic", detect_deterministic)
graph.add_node("call_llm", build_call_llm_node(llm_client))
graph.set_entry_point("detect_deterministic")
graph.add_conditional_edges(
    "detect_deterministic", route_after_deterministic, {END: END, "call_llm": "call_llm"}
)
graph.set_finish_point("call_llm")

route_after_deterministic is the routing function: it returns END if detect_deterministic already found a matching role, or "call_llm" to fall through to the LLM node otherwise.

Finally, GraphLanguageClassifier is the public-facing class that MessageGateway now depends on. It invokes the graph and interprets the final state: if role was already set by the deterministic node, return it directly; otherwise parse the LLM's raw text output (lowercased, stripped) through _classify again, and raise UnsupportedLanguageError(base=..., target=...) if even the LLM came back empty-handed.

The module also defines FakeLanguageClassifier — a trivial test double that always returns a fixed (iso_code, role) pair, used throughout the test suite wherever a real classifier isn't the point of the test.

2. Shared plumbing: bot/llm_interface.py

The new graph needs an LLM-calling node, and llm_interface.py already had one — just not in reusable form. It lived as a closure inside _build_completion_graph(). This PR lifts it out into its own factory function:

BeforeAfter
call_llm was defined inline inside _build_completion_graph(inner), private to that one graph. build_call_llm_node(inner) is a standalone function returning the same node closure; _build_completion_graph now just calls it.

This is a pure extraction — behavior is identical for the existing completion graph — but it means language_detection.py can call build_call_llm_node(llm_client) to get an LLM node for its own graph without duplicating the "call the client, stash the text in output" logic.

3. Replacing the old dependency: bot/gateway.py

MessageGateway used to depend on a bare LanguageDetector (just detect(text) -> str) and did the base/target comparison itself. It now depends on the higher-level LanguageClassifier protocol:

@runtime_checkable
class LanguageClassifier(Protocol):
    async def classify(self, text: str, language_pair: LanguagePair) -> tuple[str, LanguageRole]: ...

The inline three-way comparison and the direct raise UnsupportedLanguageError() both disappear from gateway.py — that responsibility now belongs entirely to whatever LanguageClassifier is injected. MessageGateway.process() becomes:

detected_iso, role = await self._language_classifier.classify(text, language_pair)

return AnchorMessage(
    text=text,
    detected_language=detected_iso,
    language_role=role,
)

Because classify() is async (it may need to await an LLM call), process() itself had to become async def process(...) — a ripple that reaches all the way out to MessageTrigger.

4. Wiring: bot/main.py and bot/triggers/message.py

In main.py, construction order matters now: the LLM client has to exist before the classifier can be built, because the classifier needs it for its fallback node.

llm = LangGraphLLMClient(inner=OpenAILLMClient(api_key=OPENAI_API_KEY, model=MODEL_NAME))
language_classifier = GraphLanguageClassifier(
    language_detector=LinguaLanguageDetector(), llm_client=llm
)
gateway = MessageGateway(authorizer=authorizer, language_classifier=language_classifier)

In message.py, the trigger now awaits the now-async process() call, and forwards the error's format_kwargs as discussed above:

anchor = await self._gateway.process(update, language_pair)
...
except UserFacingError as exc:
    await update.message.reply_text(
        self._localizer.t(type(exc), session.base_language, **exc.format_kwargs)
    )

5. Tests

The test suite follows the production code closely. test_gateway.py swaps every FakeLanguageDetector for a FakeLanguageClassifier and adds await to every call to gw.process(...); a new _RaisingClassifier test double stands in for "the classifier gave up," letting the gateway-rejection tests assert UnsupportedLanguageError is still propagated correctly. test_message.py adds a whole new test class, TestMessageTriggerUnsupportedLanguage, which is really the regression test for Bug #1 — it asserts the user actually receives a reply (rather than silence) containing both the base and target codes, and that no translation action runs. And the brand-new test_language_detection.py tests the graph directly: deterministic matches never touch the LLM (enforced via an _ExplodingLLMClient that fails the test if complete() is ever called), while a deterministic miss correctly routes to and is rescued by a FakeLLMClient.
