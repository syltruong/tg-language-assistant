1. Background

1.1 For beginners: why this bot needs a database at all

The tg-language-assistant bot sits inside a Telegram chat and helps someone who's mid-conversation with a native speaker: it translates, corrects grammar, suggests replies, and generally acts as a fast, low-friction aide. Everything about it, so far, has been built to be ephemeral — your language pair, your message history, which action produced which reply — all of that lives in context.user_data, a plain Python dictionary that python-telegram-bot (PTB) keeps in memory per user. The moment the process restarts, it's gone. That has been fine, because nothing in the bot has needed to survive a restart yet.

This PR is the first brick in changing that. The team has decided to add an explicit memory feature: when a Saved Insight — a whole snapshot of a conversation turn, not a lone vocabulary word — is worth keeping, the user can tap Save and have the bot remember it across restarts, redeploys, weeks. That requires an actual database, because "remember it" is precisely the one property in-memory dictionaries don't have.

SQLite is the storage engine chosen for this (see docs/adr/0001-sqlite-first-with-repository-abstraction.md): a database that lives entirely inside one file on disk, with no separate server process to run. That fits a bot that runs as a single process with a modest number of users — you get durable storage without standing up PostgreSQL. The trade-off, acknowledged directly in the ADR, is that SQLite has a single writer at a time, so it will need to be swapped out if the bot ever scales to multiple concurrent instances. To make that swap painless later, the ADR calls for a repository abstraction: application code should talk to an interface like "Insight Repository" or "User Repository," never to raw SQL, so that only the repository's internals need to change if the backend ever does.

This PR is not that repository layer. If you read the commit history, you'll see this project is being built in explicit, small PRs: PR 0/4 (already landed on the base branch) added the Saved Insight concept to the domain vocabulary in CONTEXT.md and wrote ADR-0006 explaining why a Saved Insight is captured as a raw, unprocessed snapshot rather than something an LLM has cleaned up. This PR, PR 1/4, is purely the plumbing underneath all of that: a way to open a SQLite file, make sure its schema is up to date, and keep the connection alive for the life of the bot process. The repository classes that will actually read and write Saved Insights come in a later PR, sitting on top of what's built here.

Key concept — Saved Insight From CONTEXT.md: "An immutable snapshot of one Conversation Turn that the user explicitly chose to keep. Captures the Anchor Message, the Action that produced the result, the rendered result text, and the Language Pair in force at the time." No LLM call happens when you save — it's a verbatim copy, because (per ADR-0006) a summary can always be recomputed from the raw material later, but material thrown away at save time is gone for good.

1.2 Just before this PR

Zoom in on bot/main.py, the process entry point. Before this change, its main() function did one thing to get the bot running:

bot/main.py — before 
app = ApplicationBuilder().token(TOKEN).concurrent_updates(True).build()

ApplicationBuilder is PTB's fluent builder for the bot application: you chain configuration calls onto it and finish with .build(). Nothing here touches disk. The bot's dependencies — the language detector, the LLM client, the action registry — are all constructed as plain Python objects with no persistent state, following this codebase's stated preference for constructor injection over global state or mock.patch-able module functions.

There was also no bot/storage/ package, no migrations directory, and no aiosqlite dependency — this PR introduces all three from scratch. That's the gap this PR fills: give the bot somewhere durable to write to, in a way that fits the repository-abstraction plan from ADR-0001 and is ready for the Saved Insight schema that ADR-0006 already described in prose.

2. Intuition

Strip away the file names and this PR does three things, in this order of importance:

  1. Defines a Database class that knows how to open a SQLite file and bring its schema up to date by running any .sql migration files it hasn't applied yet.
  2. Wires that class into the bot's startup and shutdown, so the connection opens before the bot starts handling Telegram updates and closes cleanly when the process stops.
  3. Makes sure the file survives a deploy in production, by mounting a persistent volume on Fly.io at the path where the database lives.

2.1 A migration runner, minimally

The core problem a migration runner solves: your schema will change over time (new tables, new columns), but you don't want to manually remember, for every environment, "did I already run the SQL that creates the saved_insights table?" The classic answer is to number your migrations and track how far you've gotten.

Most frameworks do this with a bookkeeping table — something like schema_migrations that records one row per applied migration. This PR takes a shortcut that only works because SQLite happens to give you a free integer to store exactly this: PRAGMA user_version, a 32-bit integer baked into every SQLite file's header, that starts at 0 and is otherwise unused by SQLite itself. Instead of a table, the Database class just asks "what's user_version right now?", then runs every .sql file in bot/storage/migrations/ whose leading number is higher than that, in order, bumping user_version after each one.

day 1
Fresh deploy. File bot.db doesn't exist yet. connect() creates it; PRAGMA user_version reads 0. Only 0001_saved_insights.sql is pending → it runs, user_version becomes 1.
day 40
Bot restarts (deploy of an unrelated change). user_version is already 1, and the only migration on disk is 0001 — nothing is pending. Startup is a no-op on the schema.
day 90
A future PR ships 0002_add_vocabulary_index.sql alongside code changes. On the next deploy, user_version is 1, so 0002 — and only 0002 — is pending. It runs once; user_version becomes 2. Every row inserted between day 1 and day 90 is untouched.
The database's whole "have I run this yet" memory is one integer per file — there is nothing else to keep in sync.

This is a deliberate simplification, not an oversight: because migrations are just numbered files on disk and the number in the filename is the version, there's genuinely nothing else worth recording. A bookkeeping table would only be duplicating information already implicit in the filenames.

Concrete example Say bot/storage/migrations/ contains 0001_saved_insights.sql only, and a fresh bot boots against an empty data/bot.db. The runner reads user_version = 0, globs the migrations directory, parses "0001_saved_insights.sql".split("_")[0] → 1, sees 1 > 0, and executes the whole file as one script — CREATE TABLE saved_insights (...) plus its index — then sets PRAGMA user_version = 1 and commits. Restart the bot right now, with no schema changes: user_version reads back as 1, no migration has a number greater than that, and connect() does nothing beyond opening the file.

2.2 Wiring it into the bot's lifecycle

Opening a SQLite connection is an async operation (aiosqlite.connect(...) is awaited), but main() itself is a synchronous function — it builds the PTB application and then calls a blocking method like app.run_polling(), which owns the event loop from that point on. So the connection can't just be opened at the top of main() with a bare await.

PTB's ApplicationBuilder anticipates exactly this shape of problem: it accepts post_init and post_shutdown callbacks, async functions that PTB itself awaits inside its own event loop — one right after the application initializes (before it starts receiving updates), one right after it stops. That is precisely "run this async setup/teardown code at the right point in an async lifecycle I don't otherwise control," so this PR hangs database.connect() and database.close() off those two hooks.

Startup and shutdown of the SQLite connection are pinned to the same lifecycle PTB already manages for the Telegram application — no separate event loop bookkeeping needed.

Notice, too, that database is a single object created once in main() and closed over by both callbacks — there's exactly one Database instance, and therefore one aiosqlite connection, for the whole process lifetime. That single connection is what a future PR's Insight Repository and User Repository classes will receive via constructor injection (following this codebase's stated preference for injecting concrete implementations rather than reaching for globals) — this PR just makes sure something is there to inject by the time handlers run.

2.3 Why Fly needs a volume too

A SQLite database is "just a file," which is exactly what makes it fragile in a container-based deployment. Fly.io, where this bot is hosted (see fly.toml), runs the app as a container image on a virtual machine. By default, a container's filesystem is ephemeral: every time you deploy, Fly builds a fresh machine from the image and the old filesystem — including anything the running process wrote to disk, like data/bot.db — is discarded.

A Fly volume is storage that outlives any one machine — this PR's [mounts] block in fly.toml tells Fly to attach it at /app/data, the directory DB_PATH points into.
Edge case worth knowing The comment added above the [mounts] block spells out an operational gotcha this PR doesn't (and can't) automate away: the named volume (data) has to be created once, out of band, via flyctl volumes create data --region fra --size 1, before the first deploy that includes this fly.toml. If that step is skipped, the machine fails to boot, because Fly can't mount a volume that doesn't exist. This is exactly the kind of manual, one-time infrastructure step that tends to bite whoever runs the next deploy — which is presumably why it's called out in a comment right next to the block that depends on it.

3.1 bot/storage/db.py — the Database class

This is the heart of the PR. It's a small class with exactly three public operations: connect, close, and a connection property for callers to actually run queries against.

bot/storage/db.py 
class Database:
    def __init__(self, path, migrations_dir=_MIGRATIONS_DIR):
        self._path = Path(path)
        self._migrations_dir = migrations_dir
        self._connection = None

    @property
    def connection(self):
        if self._connection is None:
            raise RuntimeError("Database is not connected. Call connect() first.")
        return self._connection

    async def connect(self):
        self._path.parent.mkdir(parents=True, exist_ok=True)
        self._connection = await aiosqlite.connect(self._path)
        self._connection.row_factory = aiosqlite.Row
        await self._migrate()

    async def close(self):
        if self._connection is not None:
            await self._connection.close()
            self._connection = None

A few choices worth calling out:

  • migrations_dir is a constructor parameter, defaulting to the real bot/storage/migrations/ directory but overridable. This is what lets the tests point a Database at a scratch directory of fake migrations without touching the real schema files — the same constructor-injection instinct the rest of the codebase applies to LLM clients and feedback clients, applied here to "where do migrations live."
  • connection raises loudly if you use it before connect(), rather than silently returning None and letting a caller crash three frames deeper on NoneType has no attribute execute.
  • row_factory = aiosqlite.Row makes query results indexable by column name (row["anchor_text"]) instead of only by position — you'll see this used directly in the tests.
  • mkdir(parents=True, exist_ok=True) before connecting means the first-ever boot in a fresh environment (no data/ directory yet) doesn't fail — SQLite will happily create the .db file itself, but not the parent directory.

The migration logic is the other half:

bot/storage/db.py 
async def _migrate(self):
    current = await self._current_version()

    for version, path in self._pending(current):
        logger.info("Applying migration {}", path.name)
        await self.connection.executescript(path.read_text(encoding="utf-8"))
        await self.connection.execute(f"PRAGMA user_version = {version}")
        await self.connection.commit()

async def _current_version(self):
    cursor = await self.connection.execute("PRAGMA user_version")
    row = await cursor.fetchone()
    return row[0]

def _pending(self, current):
    migrations = [
        (int(path.name.split("_")[0]), path)
        for path in self._migrations_dir.glob("*.sql")
    ]
    return sorted((m for m in migrations if m[0] > current), key=lambda m: m[0])

_pending is the whole "have I run this yet" logic: glob every .sql file, take the numeric prefix before the first underscore as its version (0001_saved_insights.sql → 1), keep only the ones numbered higher than the currently-recorded version, sort ascending. _migrate then applies each survivor in order, using executescript (which runs a whole file of possibly-multiple SQL statements) and commits after each one so that a later migration failing doesn't roll back an earlier one that already succeeded.

The one line that looks like it should make a security reviewer's eyebrow twitch is the f-string: f"PRAGMA user_version = {version}". Normally, interpolating a value into SQL instead of binding it as a parameter is exactly how SQL injection happens. The code comment addresses this directly — SQLite's PRAGMA statements don't accept bound parameters at all, and version is never user-supplied: it's an integer the code itself parsed out of a filename that only a developer, committing to the repository, can add. There's no path from a Telegram user's input to this string.

3.2 The first migration

0001_saved_insights.sql is where the Saved Insight concept from CONTEXT.md and ADR-0006 (both written in the prior, docs-only PR) finally becomes a real table:

bot/storage/migrations/0001_saved_insights.sql 
CREATE TABLE saved_insights (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    user_id           INTEGER NOT NULL,
    chat_id           INTEGER NOT NULL,
    slot_message_id   INTEGER NOT NULL,
    anchor_text       TEXT    NOT NULL,
    detected_language TEXT    NOT NULL,
    base_language     TEXT    NOT NULL,
    target_language   TEXT    NOT NULL,
    action_type       TEXT    NOT NULL,
    result_text       TEXT    NOT NULL,
    parse_mode        TEXT,
    run_id            TEXT,
    created_at        TEXT    NOT NULL,
    deleted_at        TEXT,

    UNIQUE (user_id, chat_id, slot_message_id, action_type)
);

CREATE INDEX idx_saved_insights_user_created
    ON saved_insights (user_id, created_at DESC);

Every column here has a direct justification in the domain docs from the earlier PR, which is a nice example of documentation written before code paying off:

  • anchor_text, detected_language, action_type, result_text, parse_mode — the raw, rendered snapshot ADR-0006 insists on: "the rendered result text ... exactly as displayed," stored with its parse_mode so it can be redisplayed identically without re-running any formatter.
  • base_language / target_language — the Language Pair "in force when it was saved, not the user's current one" (CONTEXT.md's Relationships section), because a user's target language can change after the save.
  • run_id is nullable — ADR-0006 is explicit that capture must never depend on Session, and run_id is the one field that happens to live in Session, so it's allowed to be missing.
  • deleted_at exists "from the first migration" per the ADR, even though no delete UI ships yet — soft deletion, never a row removal, keeps the append-only guarantee intact if deletion is added later.
  • The UNIQUE (user_id, chat_id, slot_message_id, action_type) constraint is the idempotency rule from the ADR, enforced by the database rather than application logic: re-tapping Save on the same slot message with the same action is a no-op (a duplicate insert), while running Analyze and then Correct on the same turn produces two distinct rows, because action_type differs.
Note This migration only creates the table — no application code in this PR ever inserts into or reads from it. That's intentional: this PR is the storage foundation, and the Insight Repository that will actually implement "save" and "list my saved insights" against this table is scoped to a later PR in the same four-part series.

3.3 Wiring: config, main.py, fly.toml

bot/config/__init__.py gains one new setting, following the existing pattern of every other config value in that file (read from an environment variable, sensible default, one-line comment explaining any non-obvious constraint):

bot/config/__init__.py 
# SQLite file backing the repositories (ADR-0001). In production this must sit
# on the mounted Fly volume — see [mounts] in fly.toml — or it is wiped on deploy.
DB_PATH = os.getenv("DB_PATH", "./data/bot.db")

bot/main.py then does the wiring described in 2.2 — construct one Database, register two small async closures as PTB lifecycle hooks:

bot/main.py 
database = Database(path=DB_PATH)

async def connect_database(_app) -> None:
    await database.connect()
    logger.info("Database ready at {}", DB_PATH)

async def close_database(_app) -> None:
    await database.close()

app = (
    ApplicationBuilder()
    .token(TOKEN)
    .concurrent_updates(True)
    .post_init(connect_database)
    .post_shutdown(close_database)
    .build()
)

And fly.toml gets the volume mount discussed in 2.3, pinned to /app/data — matching the container's working directory, so DB_PATH's default of ./data/bot.db resolves onto the mounted volume without needing an environment-specific override.

Rounding out the wiring: aiosqlite is added to pyproject.toml's dependency list (and uv.lock is regenerated to match), and .gitignore picks up a data/ entry so that a developer running the bot locally doesn't accidentally commit their own data/bot.db scratch file.

3.4 The tests

bot/storage/test_db.py has two test classes, and both are worth reading closely because each one is pinned to a specific way this code could quietly misbehave.

TestDatabaseSchema checks the basics: connecting to a brand-new file creates the saved_insights table, and — more importantly — reconnecting to an existing, populated file does not disturb its data. That second test inserts a row, closes the connection, opens a fresh Database instance against the same path, and asserts the row is still there. This is the test that would catch a migration runner bug where migrations re-run every time regardless of user_version (e.g. blindly running every file's CREATE TABLE on every boot, which would raise "table already exists" at best or wipe data at worst).

TestDatabaseMigrations is more targeted, and constructs fake two-migration sequences in a tmp_path rather than depending on the real 0001 migration:

bot/storage/test_db.py (abridged) 
async def test_applies_migrations_in_filename_order(self, tmp_path):
    """0002 alters a table 0001 creates — the wrong order raises 'no such table'."""
    ...
    (migrations / "0001_create.sql").write_text("CREATE TABLE widgets (id INTEGER);")
    (migrations / "0002_alter.sql").write_text("ALTER TABLE widgets ADD COLUMN label TEXT;")
    db = Database(path=tmp_path / "bot.db", migrations_dir=migrations)
    await db.connect()
    cursor = await db.connection.execute("SELECT id, label FROM widgets")
    assert await cursor.fetchall() == []

This test doesn't just check that migrations ran — it checks they ran in the right order, by making the second migration depend on a table the first one creates. If _pending's sort were wrong (say, sorting filenames lexicographically as strings instead of their parsed integer versions — which would break the moment a tenth migration, 0010_..., sorted before 0002_...), this test would fail with a SQLite error rather than a subtle wrong-order bug.

The second migration test, test_applies_only_migrations_newer_than_the_current_version, connects once with only 0001 on disk, closes, then writes 0002 to the same directory and reconnects — simulating exactly the "day 90" scenario from the timeline diagram in 2.1: a migration that ships after a database already has real data in it. It asserts the previously-created table survives and gains the new column, i.e. that _pending correctly filters out 0001 (already applied) and runs only 0002.
