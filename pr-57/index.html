1. Background

1.1 How a message becomes a reply, from scratch

If you already know this codebase well, feel free to skip to §1.2. If not, here is the shape of the system this PR sits inside.

tg-language-assistant is a Telegram bot that helps someone chatting with a native speaker in a language they're still learning. The user sends a message in French (say), and the bot instantly translates it — no button tap required. That automatic first response is called an Instant Action; the default one is Translate.

User's Telegram message
"Comment ça va?"
→
MessageGateway
→
MessageTrigger
→
ActionRunner
→
ResponsePublisher
→
Bot's reply
"How's it going?"

The Instant Action pipeline. MessageGateway authorizes and classifies the incoming text; ActionRunner calls the LLM and formats the result; ResponsePublisher posts it to Telegram as a reply to the original message.

The bot's reply — the "Slot Message" in this codebase's vocabulary — doesn't just sit there. It arrives with a row of buttons underneath it: Analyze, Correct, Rephrase, Reply. Tapping any of these is a Keyboard Action: the bot re-runs a different prompt against the same anchor text and edits the same message in place rather than sending a new one. So across an entire back-and-forth with these buttons, there's exactly one bot message per turn, its content changing underneath a keyboard that stays put.

Definition — Conversation Turn & Slot Message

A Conversation Turn begins when the user sends a message (the Anchor Message) and produces exactly one bot message, the Slot Message. Every Keyboard Action the user taps afterwards — Analyze, Correct, Rephrase, Reply — edits that same Slot Message rather than posting a new one. The keyboard lives on the Slot Message for the whole turn.

Below the four action buttons sits a second, older feature: a rating row. "Rate this response:" followed by 👍 / 👎 / Skip. Tapping a thumb calls FeedbackTrigger, which records the vote against the LLM trace that produced the message, then removes the rating row entirely (via strip_rating_rows) so it can only be tapped once.

All of this per-user state — which language pair is active, which Action rendered which Slot Message, what suggestions are pending — lives in UserSession, a thin typed wrapper around Telegram's context.user_data dictionary. It is in-memory only: it evaporates if the bot process restarts. That fact turns out to matter a great deal for this PR, as you'll see in §3.5.

1.2 What already existed before this PR

This PR is the third of four building a new capability: letting the user explicitly keep a turn forever, rather than letting it scroll off into Telegram history. The commit history calls it "PR 3/4 — the Save button", and the branch it's diffed against already contains PRs 1 and 2:

Already in place (base branch)Purpose
bot/insights.py — SavedInsight, InsightRepositoryProtocol, InMemoryInsightRepository, SqliteInsightRepository The write/read model and both a fake and a real implementation of where a kept turn lives.
SQLite migration for a saved_insights table Persistent storage, with a UNIQUE constraint and a soft deleted_at column.
docs/adr/0006-saved-insights-capture-raw-turns.md The design decision this PR must honour (see callout below).

What was missing — and what this PR adds — is everything between the user's thumb and that repository: a Save button on the keyboard, a trigger that assembles a SavedInsight from what's on screen, and the plumbing to wire it all together in main.py.

ADR-0006 — the constraint this PR has to honour

A Saved Insight is a verbatim snapshot of a turn — anchor text, detected language, language pair, which Action produced the result, and the rendered result exactly as displayed. No LLM call happens on the write path, and no interpretation of the text happens either. Two consequences that shape the code below: the natural key for de-duplication is (user_id, chat_id, slot_message_id, action_type), and — most importantly — capture is designed to not depend on Session, because Session is volatile and the user believes they've kept something the moment they tap the button.

Picture a learner mid-conversation. They sent a French sentence, the bot translated it, and now they want to remember this exchange for later review. Here's the keyboard before and after they tap the new button:

👍
👎
Skip
✅ Saved

Everything else on the keyboard is untouched — the Save row is inserted between the four action buttons and the rating row.

Under the hood, nothing about the message text

Here's the twist that makes this genuinely interesting rather than a simple boolean flag: the "saved" state isn't a property of the Slot Message, it's a property of this particular rendered result. Suppose our learner, having saved the translation, now taps Correct. The same Slot Message is edited in place to show a corrected sentence — and the Save button resets to "💾 Save", not "✅ Saved":

slot_message_id=42
action_type="translate"
✅ Saved
tap "Correct" on same message →
slot_message_id=42
action_type="correct"
💾 Save

Same Slot Message, different Action — a fresh row in the saved_insights table, so a fresh "unsaved" starting state.

That falls straight out of the natural key from ADR-0006: (user_id, chat_id, slot_message_id, action_type). The translation and the correction are two different Saved Insights waiting to happen, even though they live, one after another, in the very same Telegram message. Once you see that the "unit of Saved-ness" is really "an Action's result", the rest of the code follows naturally.

3. Code walkthrough

3.1 Three new strings in the catalog

Every user-facing string in this codebase has to be registered as a MsgKey in bot/config/messages.py rather than hardcoded — that's a hard rule enforced by the project's own conventions. This PR adds exactly the three strings the feature needs:

bot/config/messages.py
class MsgSave(MsgKey):
    pass

class MsgSaved(MsgKey):
    pass

class MsgSaveFailed(MsgKey):
    pass

# ...in the English catalog:
MsgSave: "💾 Save",
MsgSaved: "✅ Saved",
MsgSaveFailed: "Couldn't save that one. Please try again.",

Nothing clever here — but it's the seam that lets every other file below ask for t(MsgSaved) instead of typing "✅ Saved" inline, keeping localisation centralised.

3.2 From a constant to a function

Before this PR, bot/keyboard.py built one InlineKeyboardMarkup called KEYBOARD exactly once, at import time, and every trigger just referenced that same frozen object. That worked because the keyboard never varied — same four action buttons, same rating row, always.

The Save button breaks that assumption: its label depends on whether this specific result has already been kept. A single module-level constant can't hold two different labels at once, so KEYBOARD becomes build_action_keyboard(saved: bool = False) — a function called fresh, every time a Slot Message is rendered:

bot/keyboard.py
SAVE_PREFIX = "save:"
SAVE = f"{SAVE_PREFIX}insight"

def build_action_keyboard(saved: bool = False) -> InlineKeyboardMarkup:
    """The standard keyboard for a Conversation Turn.

    Built per message rather than once at import, because the Save button
    reflects whether this turn has already been kept.
    """
    return InlineKeyboardMarkup(
        [
            [Analyze, Correct],   # unchanged
            [Rephrase, Reply],    # unchanged
            [InlineKeyboardButton(t(MsgSaved if saved else MsgSave), callback_data=SAVE)],
            *_rating_rows(),
        ]
    )

Every call site that used to import the constant KEYBOARD now calls build_action_keyboard() instead — three production files (bot/triggers/message.py, bot/triggers/keyboard.py, and the new bot/triggers/save.py) and every test that asserted against the old constant. It's the single largest mechanical change in the diff, but conceptually shallow: a global becomes a factory, called at the same points it used to be referenced.

Notice where the new row lands: after the four action buttons, before the rating rows. That ordering is what produces the "Save resets on a new Action, rating row does not" behaviour from §2 — the rating row is tied to the trace of whichever Action most recently ran, and stays wherever it already was relative to the bottom of the keyboard.

3.3 Making strip_rating_rows content-aware

FeedbackTrigger needs to remove the rating row once the user has voted, so it can't be tapped twice. Previously it did this positionally:

bot/keyboard.py — before
def strip_rating_rows(markup: InlineKeyboardMarkup) -> InlineKeyboardMarkup:
    """Return a copy of markup with its last two rows (the rating label + thumbs rows) removed."""
    return InlineKeyboardMarkup(list(markup.inline_keyboard[:-2]))

That's fragile by construction: it silently assumes the rating rows are always exactly the last two rows on any keyboard it's handed. Since this PR is already restructuring build_action_keyboard and inserting a new row into the mix, the author took the opportunity to make the function robust rather than merely correct-by-luck. The rewrite identifies rows by their callback_data prefix instead of their position:

bot/keyboard.py — after
def _is_rating_row(row) -> bool:
    return any((btn.callback_data or "").startswith(RATE_PREFIX) for btn in row)

def strip_rating_rows(markup: InlineKeyboardMarkup) -> InlineKeyboardMarkup:
    """Return a copy of markup with the rating label + thumbs rows removed.

    Identifies the rows by their callback data rather than by position, so
    adding a row to the keyboard cannot silently strip the wrong one.
    """
    return InlineKeyboardMarkup(
        [row for row in markup.inline_keyboard if not _is_rating_row(row)]
    )
Analyze / Correct
Rephrase / Reply
💾 Save
Rate this response:
👍 👎 Skip
Full keyboard, 5 rows
Analyze / Correct
Rephrase / Reply
💾 Save
Rate this response:
👍 👎 Skip
After a rating tap — only rate:* rows dropped

The filter matches on callback_data.startswith("rate:"), so it keeps working no matter how many rows sit above or below the rating rows.

3.4 Session learns which Action rendered a slot

A SavedInsight needs an action_type field — which Action (translate, correct, analyze…) produced the text currently on screen. Nothing previously recorded that anywhere reachable at Save time, so UserSession gains a small, symmetrical pair of methods:

bot/session.py
_KEY_SLOT_ACTIONS = "slot_actions"

def store_slot_action(self, msg_id: int, action_type: str) -> None:
    """Record which Action produced what is currently rendered in a slot message."""
    self._data.setdefault(self._KEY_SLOT_ACTIONS, {})[msg_id] = action_type

def get_slot_action(self, msg_id: int) -> str | None:
    return self._data.get(self._KEY_SLOT_ACTIONS, {}).get(msg_id)

Both MessageTrigger (the Instant Action path) and KeyboardTrigger (every subsequent Keyboard Action) now call session.store_slot_action(msg_id, action_type) right after publishing or editing the Slot Message — so by the time Save is tapped, whatever the user is currently looking at has its Action type recorded against that message id. This mirrors the pre-existing store_run_id / get_run_id pair used for correlating a Slot Message to its LangSmith trace.

3.5 The new SaveTrigger

This is the centrepiece of the diff — a brand-new file, bot/triggers/save.py, following the same constructor-injection shape as every other trigger in the codebase (a Protocol dependency passed in, no module-level state, no mock.patch needed to test it).

bot/triggers/save.py
class SaveTrigger:
    def __init__(self, repository: InsightRepositoryProtocol) -> None:
        self._repository = repository

    async def handle(self, update: Update, context: ContextTypes.DEFAULT_TYPE) -> None:
        query = update.callback_query
        session = UserSession.from_context(context)
        slot_id = query.message.message_id
        language_pair = session.language_pair

        anchor = getattr(query.message, "reply_to_message", None)
        insight = SavedInsight(
            user_id=update.effective_user.id,
            chat_id=query.message.chat.id,
            slot_message_id=slot_id,
            anchor_text=(getattr(anchor, "text", "") or "").strip(),
            detected_language=session.get_detected_language(slot_id) or language_pair.target,
            base_language=language_pair.base,
            target_language=language_pair.target,
            action_type=session.get_slot_action(slot_id) or UNKNOWN_ACTION,
            result_text=query.message.text_html or query.message.text or "",
            parse_mode="HTML" if query.message.text_html else None,
            run_id=session.get_run_id(slot_id),
        )

        try:
            await self._repository.save(insight)
        except Exception as exc:  # never break the Telegram flow
            logger.warning("Could not save insight: {}", exc)
            await query.answer(t(MsgSaveFailed, session.base_language))
            return

        await query.answer(t(MsgSaved, session.base_language))
        await query.edit_message_reply_markup(reply_markup=build_action_keyboard(saved=True))

The interesting design decision is where each field comes from. Look closely and two sources are in play:

Telegram callback
query.message
anchor_text
result_text · parse_mode
chat_id · slot_message_id
+
UserSession
(in-memory, volatile)
action_type (or "unknown")
run_id (nullable)
detected_language (fallback)
→
SavedInsight

Everything load-bearing comes off the callback itself, which Telegram guarantees is there. Session only supplies extras whose absence degrades gracefully instead of failing the Save.

This is a deliberate departure from how FeedbackTrigger and suggestion-selection behave elsewhere in the codebase. Both of those silently no-op if Session has been lost (e.g. the bot process restarted mid-conversation) — acceptable, because the cost is one dropped tap on a rating or a suggestion. Save is different: the moment the user sees the button flip and the "✅ Saved" toast, they believe the turn is safely kept. Silently no-op'ing there would be a lie. So SaveTrigger is written so that even a completely empty Session still produces a valid SavedInsight — just with action_type="unknown" and run_id=None instead of failing.

Edge case — repository dedup vs. user feedback

InsightRepositoryProtocol.save() returns None when the natural key already exists (a second tap on an already-saved result). SaveTrigger doesn't inspect that return value — it always answers "✅ Saved" and flips the button on any non-exception outcome. That's intentional: from the user's point of view, tapping Save on something already saved should look identical to tapping it the first time — idempotent in effect, not just in storage.

Errors are handled the same way the rest of the bot handles unreliable external calls (LangSmith feedback, LangSmith tracing): catch broadly, log, tell the user gently via MsgSaveFailed, and — critically — never let a storage failure break the Telegram response flow.

3.6 Wiring it into main.py

Three additions tie the new trigger into the running application: build a SqliteInsightRepository against the shared Database, construct a SaveTrigger with it, and register a CallbackQueryHandler that only matches callback data starting with save:.

bot/main.py
save_trigger = SaveTrigger(repository=SqliteInsightRepository(database=database))
...
app.add_handler(
    CallbackQueryHandler(feedback_trigger.handle, pattern=f"^{RATE_PREFIX}")
)
app.add_handler(
    CallbackQueryHandler(save_trigger.handle, pattern=f"^{SAVE_PREFIX}")
)
app.add_handler(CallbackQueryHandler(keyboard_trigger.handle))  # catch-all, last

Handler order matters here, and the existing comment above the feedback handler ("must be registered before the catch-all keyboard handler, otherwise rate:* callback data reaches KeyboardTrigger and raises a KeyError") applies equally to save:* — python-telegram-bot tries handlers in registration order and stops at the first pattern match, so the save handler has to sit above the unpatterned catch-all that would otherwise try to interpret "save:insight" as an ActionType and blow up.

3.7 Tests and the update to factories.py

The test suite grows in two ways. First, every existing test that imported the old KEYBOARD constant is updated to call build_action_keyboard() instead (mechanical, following from §3.2). Second, a new bot/triggers/test_save.py exercises SaveTrigger end to end against the existing InMemoryInsightRepository fake — no mocking of the repository is needed, because it was already designed as a real, swappable implementation rather than a test double bolted on afterwards.

The tests cover exactly the design decisions discussed above: the happy path, "keeps the turn even when the session is gone" (the ADR-0006 guarantee from §3.5), "a second tap does not keep the turn twice", and "a failing repository tells the user instead of raising".

To make the session-loss and action-type tests possible, tests/factories.py's make_callback_update gains a slot_text parameter that stamps the fake message's .text and .text_html attributes — simulating the Action result currently rendered on screen, which is exactly what SaveTrigger reads to populate result_text.
