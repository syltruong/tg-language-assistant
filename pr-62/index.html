Background

The deep background: how a GitHub Actions pipeline talks to GitHub Pages

If you've never wired up GitHub Actions to GitHub Pages before, here's the short version, and you can skip ahead to the next subsection if this is already old hat. A GitHub Actions workflow is a YAML file living under .github/workflows/ that says "when event X happens, run these steps." GitHub Pages, meanwhile, is a static-site host baked into every GitHub repo: point it at a branch (conventionally called gh-pages), and whatever files sit in that branch become a website at https://<owner>.github.io/<repo>/.

Put those two together and you get a very common pattern: a workflow that triggers on some event, generates an HTML file, and pushes it into the gh-pages branch so it's browsable on the web — no server to run, no hosting bill, just files in a branch.

The narrow background: this repository's "explain diff" pipeline

This repository uses exactly that pattern to explain its own pull requests. In fact, the very page you're reading right now was produced by it. Here's the pipeline, defined in .github/workflows/explain-diff.yml, which already exists on master and is untouched by this PR:

PR opened / updatedpull_request event
→
Claude generates HTMLruns /explain-diff-html
→
Deploy to gh-pagesfolder pr-<number>/
→
Comment on the PRwith a link to the page

Every push to a pull request re-runs this, so the explanation folder for, say, PR 53 lives at gh-pages/pr-53/index.html and stays up to date as the PR evolves. Looking at the actual gh-pages branch in this repo today, you'll find folders like pr-53/ and pr-60/ sitting there from earlier PRs.

That raises an obvious follow-up question: once a PR is merged or closed, what happens to its explanation folder? Does it just accumulate forever, or does something clean it up? That question is the entire subject of this PR — and, as you're about to see, the repo's answer to it changed its mind twice in the space of a few minutes before landing here.

Key files involved .github/workflows/explain-diff-cleanup.yml — the file this PR deletes. It never had any effect on the generation pipeline above; its only job was tidying up afterwards.

Intuition

Strip away the YAML and this PR is really about one design question: should generated documentation for a closed pull request keep existing? There are two reasonable answers, and the commit history of this very PR argues both sides before settling on one.

Option A: auto-delete on close

The original explain-diff-cleanup.yml (the version currently on master) took this position. It listened for pull_request: types: [closed], and when a PR closed it deleted that PR's folder from gh-pages. The reasoning is tidy: closed PRs are done, keeping their explanation around is clutter, so sweep it away automatically. Think of it like a whiteboard that gets erased the moment the meeting it was used for ends.

Option B: keep everything, forever

This PR's final state takes the opposite position: there should be no cleanup mechanism at all, automatic or manual. Once an explanation is published, it stays published. Think of it less like a whiteboard and more like a museum — every exhibit that ever went up stays up, so anyone can walk back through the collection later, whether that's a teammate ramping up on the project's history, or someone in six months wondering "wait, why did we make that change back in PR 53?"

Why permanence wins here The value of an explain-diff page isn't just "helping the reviewer of this one PR." It's a standing archive of why the codebase looks the way it does. Deleting that the moment a PR closes throws away exactly the artifact you'd want six months later when nobody remembers the reasoning behind a change.

The middle ground that got skipped

Interestingly, the commit history of this PR briefly stopped at a middle position — "keep it around by default, but let a human manually trigger a deletion for a specific PR number if needed" — before abandoning even that in favor of full permanence. You'll see both steps in the Code section below, because although the final diff against master is a plain deletion, the journey to get there is the more interesting story.

Step 1 — from automatic to manual

The first commit's message explains the motive directly: artifacts on gh-pages should persist after a PR closes rather than vanish automatically. Rather than deleting the workflow outright at this point, it was made opt-in: a maintainer can still run it by hand from the Actions tab, but nothing fires on its own.

Note the small but thoughtful addition of the else branch: since a human is now triggering this by typing in a PR number, it's worth telling them clearly when there was nothing to clean up, rather than silently doing nothing.

What this means for master

Because master only ever had the original, automatic version of the file (Step 1 and Step 2 both happened on this PR's branch), comparing master straight against the branch head just shows one clean deletion of that original file. The intermediate "manual dispatch" version never touches master at all — it's a stepping stone visible only in this branch's history.

FileOn masterOn this branch (HEAD)
.github/workflows/explain-diff-cleanup.yml Exists — auto-deletes on PR close Deleted entirely
.github/workflows/explain-diff.yml Unchanged Unchanged — generation pipeline is untouched
What did NOT change The explain-diff.yml workflow that generates and publishes these pages (the one described in the Background section) is completely untouched. This PR only removes the deletion side of the pipeline — publishing continues exactly as before.

One nice side effect: with no cleanup workflow left, the gh-pages branch no longer needs to grant any workflow contents: write permission for the purpose of deleting things. Fewer workflows with write access to a branch is generally a good thing from a "what could possibly go wrong" standpoint — there's simply one fewer automation with the power to force-push a deletion commit to your public site.
