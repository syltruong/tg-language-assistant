01Background

Most explanations of a code change begin with the code. This one has to begin somewhere else, because the code change is two lines of a plain-text scratch file and nothing in the running program is affected by it. Understanding this pull request means understanding the machinery it triggers. So we will build up that machinery first, then return to the diff and find it surprisingly rich.

The deep version

Skip ahead to the narrow version if you already know GitHub Actions, GitHub Pages, and three-dot diffs.

The project. tg-language-assistant is a Telegram bot for language learners holding a live conversation with a native speaker. You send it a message; it translates, corrects, analyses, or drafts a reply. Its domain vocabulary is documented with unusual care in CONTEXT.md — an Anchor Message is the message that started a turn, a Slot Message is the single bot reply that gets edited in place as you tap buttons, an Action is one self-contained unit of bot behaviour. None of these concepts change in this pull request. They matter only as the backdrop against which a plain TODO file sits in the repository root, collecting ideas that are not yet issues.

GitHub Actions. A workflow is a YAML file under .github/workflows/. It declares an event to listen for (on:), a set of jobs, and inside each job a list of steps. Each step either runs a shell command or invokes a reusable action published by someone else. When the event fires, GitHub allocates a fresh virtual machine, clones your repository into a working directory, and executes the steps in order. If any step exits non-zero, the job fails and the remaining steps are skipped.

Two details of that model do real work later in this story. First, permissions: each workflow run receives a scoped token, and it can only do what the permissions: block grants — writing to the repository, commenting on pull requests, and so on. Second, the filesystem is ephemeral and scoped: steps share the runner's disk, so one step can write a file and a later step can read it, but only paths inside the checked-out workspace are meaningful to actions that upload or commit directories.

GitHub Pages. A repository can serve static files over HTTPS from a branch. Here the branch is gh-pages, which is an orphan branch: it shares no history with master and contains no source code at all, just published output. A file committed at pr-60/index.html on that branch becomes reachable at https://syltruong.github.io/tg-language-assistant/pr-60/. This is the delivery mechanism for everything you are reading.

Key concept — three-dot diff

git diff master..HEAD compares the two endpoints: anything that landed on master after you branched shows up as a spurious reversal in your diff. git diff master...HEAD (three dots) instead compares the merge base — the last commit the two branches had in common — against your head. That is the "what did this PR change" question, and it is what a reviewer means. The instruction embedded in the workflow prompt is to diff the base branch against the current head, and three dots is how you honour it faithfully.

The narrow version: what #59 built

The commit immediately before this pull request, 2573a19 ("Add explain-diff-html skill, #59"), added three things that concern us.

One: a Claude Code skill at .claude/skills/explain-diff-html/SKILL.md. A skill is a Markdown file of instructions that a human invokes as /explain-diff-html. This one asks for a single self-contained HTML page with four sections — Background, Intuition, Code, Quiz — written in a particular register, with HTML diagrams rather than ASCII art. Crucially for CI, its output path is parameterised: it defaults to a dated file in /tmp, but honours an explicit path if the invocation supplies one.

Two: .github/workflows/explain-diff.yml, which runs that skill non-interactively on every push to a pull request, publishes the result, and comments the link.

Three: .github/workflows/explain-diff-cleanup.yml, which deletes the published folder when the pull request closes, so gh-pages does not accumulate output for merged work forever.

Edge case that already bit once

#59 needed a follow-up fix: claude-code-action@v1 fetches a GitHub OIDC token internally, so without id-token: write in the workflow's permissions block the step fails with "Could not fetch an OIDC token" before Claude is ever invoked. The final permission set is therefore three-part: contents: write to push to gh-pages, pull-requests: write to comment, and id-token: write for the action's own handshake.

That fix is the tell. A workflow of this shape has many independent ways to fail — a missing permission, a path the deploy action cannot see, a branch that does not exist yet, a comment marker that does not match — and every one of them is invisible until the thing runs end to end against the real repository. Which is exactly the gap this pull request exists to close.

02Intuition: a self-referential smoke test

The intuition is best stated as a small paradox. The pull request that introduced the explain-diff pipeline is a poor test of it: much of what the pipeline touches lives outside the pull request. The gh-pages branch has to exist. Pages has to be enabled and serving from it. The repository secret ANTHROPIC_API_KEY has to be present. The comment marker has to match a previous comment that, on a first run, is not there. As the first commit message in this pull request puts it: the workflow "can't validate itself from within the PR that first introduced it."

So you need a second pull request whose diff is deliberately, almost comically trivial — small enough that any failure is unambiguously the pipeline's fault and never the diff's. A single line appended to a scratch file is about as close to zero payload as a real commit gets. The line even names its own purpose:

- [ ] Verify explain-diff-html CI pipeline (explain-diff.yml) actually publishes
      to gh-pages and comments on PRs

Then a second push arrives — - [ ] Another trivial edit — and this is where the test stops being trivial. A first push and a second push exercise different code paths through the same YAML.

Push #1 — the create path

pr-60/ does not exist on gh-pages. The deploy action creates it. There is no comment carrying the explain-diff marker, so the sticky-comment action posts a new one.

Proves: permissions, OIDC, output path, Pages publish, comment creation.

Push #2 — the regenerate path

pr-60/index.html already exists and must be overwritten, not duplicated. A comment with the marker already exists and must be edited, not appended. And if run #1 were still going, the concurrency group would cancel it.

Proves: idempotency — the property the comment's own text promises.

That promise is written into the sticky comment: "Regenerated automatically on every push to this PR." Idempotency under repeated pushes is a claim, and push #2 is the experiment that tests it. Here is what the reviewer sees on the pull request page in the two cases — the same single comment, its body silently replaced:

That second commit is not hypothetical. Before the current run, gh-pages already held pr-60/index.html at roughly 50 KB, deployed from an earlier merge ref of this same pull request. Key concept — the missing final newline

A text file's last line ordinarily ends with \n. On master, TODO did not: its final byte was the letter r of "matter". Git tracks content, not lines, and it marks this with \ No newline at end of file. To append after such a line you must first terminate it — which changes those bytes — so git records the old unterminated line as removed and the newline-terminated version as added. One line of visual churn, zero lines of semantic change. This is why appending to a no-trailing-newline file always shows a phantom deletion, and why the second commit's diff shows the same phantom again for the line it appended after.

Not changed — worth knowing

No Python, YAML, prompt template, or documentation file is touched. Lint and tests in ci.yml run and pass, but they exercise nothing new: TODO is not imported, parsed, or asserted on anywhere. The bot's behaviour on master and on this branch is byte-for-byte identical.

What the neighbouring lines are for

One incidental benefit of reading a TODO diff closely is the context lines, which are a compact tour of the project's live design debts. Two are worth naming because they show what kind of backlog this is:

  • Action.format() should return FormattedResult directly — today an Action exposes parse_mode as a separate property (a deliberate choice, recorded in docs/adr/0002-action-parse-mode-independent-from-response-format.md) and the Action Runner assembles the pair. Returning text and parse mode together would remove that assembly step.
  • ResponsePublisher._locks grows one entry per distinct user_id, never evicted — a known unbounded-growth issue, explicitly deferred until the user base makes it matter. Not a bug report; a dated decision to wait.

The new entries join that register. "Verify explain-diff-html CI pipeline" is a note-to-self that this very run is the verification, and it stays unchecked until a human confirms the outcome.

04What the two lines actually exercise

It is worth being precise about which lines of YAML are under test, since that is the whole payload of the change. Four mechanisms in explain-diff.yml only ever engage on a repeat push, and this pull request is the first thing in the repository's history to produce one.

Concurrency

concurrency:
  group: explain-diff-${{ github.event.pull_request.number }}
  cancel-in-progress: true

The group key is per-PR, so pull requests never queue behind each other, but two runs for the same pull request cannot overlap: the newer push cancels the older run. This matters more here than in an ordinary test job, because both runs would otherwise race to commit to the same pr-60/ path on gh-pages and to edit the same comment. Cancellation is the serialisation.

A non-clean deploy into a per-PR folder

branch: gh-pages
folder: explain-diff-output
target-folder: pr-${{ github.event.pull_request.number }}
clean: false

clean: false is the load-bearing flag. With cleaning on, each deploy would wipe everything on gh-pages that is not in the uploaded folder — so publishing pr-60/ would delete pr-59/, pr-61/, and any other live explanation. With it off, the deploy is additive: it replaces the contents of the target folder and leaves siblings untouched. The cost is that stale folders never disappear on their own, which is precisely why the cleanup workflow exists as the counterweight.

The redirected output path

The default skill behaviour — write a dated file into /tmp — is right for a human at a terminal and wrong in CI, because the deploy step uploads a directory relative to the workspace. Rather than special-casing CI inside the skill, the workflow passes the destination in the prompt and the skill honours it. The mechanism is a plain instruction, and it is what makes one skill serve both an interactive session and an unattended runner.

The sticky comment marker

header: explain-diff becomes an invisible HTML marker in the comment body. On each run the action searches the pull request's comments for that marker: found, and it edits in place; absent, and it creates. One PR therefore accumulates exactly one explain-diff comment no matter how many times you push — the difference between a helpful bot and a noisy one.

Key concept — the merge ref

A pull_request run does not check out your branch tip. It checks out refs/pull/60/merge: a synthetic merge of your head into the base, which is why the local git log here shows a detached HEAD at a commit whose subject is "Merge 4f0b7b8… into 2573a19…". This is a feature — you are told what the code will look like after merging, not merely what it looks like on the branch — but it is also why the base is referred to by name (master) in the prompt rather than assumed to be HEAD~1.

05What this run can and cannot prove

Honesty about a smoke test's coverage is part of the test. Reading the branch state, the following is established, and the following is not.

established

The gh-pages branch contains pr-60/index.html, deployed unattended from an earlier run of this pull request. So: the fork guard passed, the OIDC permission was sufficient, Claude wrote to the workspace path, and the deploy step committed and pushed.

still open at the moment of writing

Whether this run overwrote that file rather than sitting beside it; whether the sticky comment was edited rather than duplicated; whether GitHub Pages is actually serving the URL; and whether the cleanup workflow removes pr-60/ when the pull request closes. That last one cannot be tested before merge by construction.

Which yields a concrete checklist for whoever ticks the TODO item off. Open the URL in the comment and confirm it renders. Confirm there is exactly one explain-diff comment on the pull request. Confirm the page describes the second commit, 4f0b7b8 — that is the proof of regeneration, since run #1 could not have known about a commit that did not yet exist. Then close the pull request and confirm pr-60/ disappears from gh-pages.

If all four hold, the mechanism is sound and the interesting question moves elsewhere: not whether the pipeline runs, but whether an explanation generated for every push is worth reading. A two-line TODO edit is a deliberately unfair trial of that — there is almost nothing to explain, so the page fills up with background and machinery. The fair trial is the next substantive pull request, where this same apparatus has a real design change to make legible.
