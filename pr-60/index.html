That is the entire diff. No Python was touched, no workflow was edited, no test was added. If you judged pull requests by lines changed, this one would not register at all.

So the change has two jobs. The content of the line records a genuine piece of unfinished business: nobody has yet watched the new explain-diff pipeline complete a full lap. The shape of it

Background

Deep background for beginners

If you already know what GitHub Actions, the gh-pages branch, and Claude Code skills are, skip ahead to the pipeline this PR is about.

The repository is tg-language-assistant, a Telegram bot for language learners. Someone mid-conversation with a native speaker sends a message to the bot and gets back a translation, a vocabulary breakdown, a grammar correction, or a few suggested replies. The domain vocabulary is written down carefully in CONTEXT.md — Anchor Message, Slot Message, Instant Action, Action Runner — and architectural decisions live as numbered ADRs under docs/adr/. It is a small codebase that takes its own documentation unusually seriously.

None of that domain machinery matters for this pull request. What matters is the scaffolding around it, and there are three pieces worth knowing.

First, continuous integration. GitHub can run programs for you in response to repository events. You describe them in YAML files under .github/workflows/. This project has a conventional one, ci.yml: on every pull request it installs dependencies, runs ruff for linting and pytest for tests; on a push to master it additionally deploys to fly.io. The unit of work is a job; a job is a list of steps; a step either runs a shell command or invokes a reusable action pinned by name and version, like actions/checkout@v4.

Second, GitHub Pages and the gh-pages convention. GitHub will serve static files straight out of a repository as a website. A long-standing convention is to keep those files on a dedicated branch named gh-pages, entirely separate from your source history, and let a bot push to it. A file at pr-60/index.html on that branch becomes a URL ending in /pr-60/. This gives you somewhere to publish build artefacts without polluting master.

Third, Claude Code skills. A skill is a Markdown file of instructions that an AI coding agent can be asked to follow, invoked like a slash command. This repo keeps several under .claude/skills/ — tdd, diagnose, triage, and others. One of them, explain-diff-html, says in effect: read a code change, explore the surrounding code until you understand it, then write a single self-contained HTML page with background, intuition, a code walkthrough, and an interactive quiz. That skill is what produced this page.

Definition · skill

A skill is a prompt-as-a-file: reusable instructions the agent loads on demand. It is not code, so nothing compiles it and no test suite checks it. Its only real specification is whether the artefact it produces is any good — which is precisely why it is awkward to verify automatically.

Finally, the TODO file. It is thirteen lines of plain text at the repository root, a flat checklist in Markdown-ish syntax. Some entries are ticked ([x] html formatting of responses), most are not. It sits alongside a more formal tracker: CLAUDE.md states that issues live in GitHub Issues, and docs/agents/issue-tracker.md spells out the gh commands for working with them. In practice the two coexist — TODO is the back of an envelope, GitHub Issues is the filing cabinet. This pull request writes on the envelope.

Intuition: a pipeline cannot vouch for itself

The bootstrapping problem

Here is the awkward position pull request #59 was in. It introduced a machine whose job is to comment on pull requests and publish web pages about them. The natural way to test such a machine is to open a pull request and watch. But the only pull request available was #59 itself — and using it as the test subject has three distinct problems.

The first is confounding. Pull request #59 added a dozen files: several skills, two workflows, supporting documents. If the pipeline had produced a mediocre explanation, was that the pipeline's fault or the diff's? A change that adds prompt files has no interesting data flow to draw, no toy example to work through. You cannot calibrate an instrument on a sample you do not trust.

The second is iteration cost. The only way to fix a workflow is to push a commit and wait. #59 took three commits to converge, one of them purely to add a missing permission. Each of those pushes is a run against a moving target, and the workflow file being executed changes underneath you between attempts.

The third, and the sharpest, is irreversible state. Steps 4 and 5 do not merely compute; they write to places outside the run. Step 4 pushes a commit to a shared long-lived branch. Step 5 mutates a comment on the pull request. And the cleanup workflow only fires on closed — an event that, for the pull request introducing the cleanup workflow, arrives at the very moment its own machinery becomes real. You cannot rehearse a step whose whole purpose is to modify the world.

The core intuition

To test a machine, hold the machine still and vary the input. Pull request #59 had to vary both at once. Pull request #60 exists to supply the boring input that #59 could not: a change so small that the pipeline is the only variable left.

Why a TODO line is the ideal payload

Suppose you need a throwaway commit to trigger a workflow. There are several stock manoeuvres, and it is instructive to see why each is worse than the one chosen here.

ManoeuvreTrouble with it
An empty commit (--allow-empty)Triggers the run, but leaves nothing behind. When someone reads the history in six months, the commit explains nothing and the follow-up work is unrecorded.
A whitespace tweak somewhere in bot/Touches production code for a non-production reason, and drags ci.yml's lint-and-test job along for a ride it does not need.
Bumping a version or a commentSame objection, plus it invites a reviewer to wonder whether the bump was meaningful.
A line in TODONothing. It is inert to lint and tests, it is honest about being a note, and the note it makes is the very thing the commit is doing.

The last row is the trick, and it is a genuinely tidy one. Most throwaway commits are pure waste: you pay a line of history for a moment of CI feedback. This one converts the waste into a record. The change is a trigger and a reminder at the same time, and the reminder is about the trigger.

What the stateful steps actually touch

It helps to picture the gh-pages branch as a filesystem that three separate agents write to. Below is that branch at three points in time — the same tree diagram, varied.

Notice how the design splits responsibility. The deploy step is deliberately additive — it never deletes, so two pull requests open at once cannot clobber each other's pages. The consequence is that something else must do the deleting, and that something is a separate workflow on a separate event. Additive writes plus a compensating cleanup is a common and sound arrangement, but it has a characteristic weakness: the compensation runs exactly once, at a moment nobody is watching, and a bug in it is silent. It shows up months later as a branch full of stale folders. That is a large part of why the TODO item is worth writing down rather than assuming.

The new entry lands at the bottom of the file, and its neighbours are worth a glance, because placement carries meaning here. The last three items before it are all deferred maintenance with a stated trigger: refactor Action.format() to return a FormattedResult directly; add TTL or LRU eviction to ResponsePublisher._locks "once the user base is large enough for this to matter". These are not features. They are known-and-parked concerns, each carrying enough context that a future reader can judge whether the moment has come.

The new line fits that mould precisely. It names the artefact (explain-diff.yml), states the two observable outcomes it wants confirmed (publishes to gh-pages; comments on pull requests), and implicitly sets its own trigger: check the next time a pull request goes by. Contrast it with a line reading "check CI works" — the version actually written can be closed by evidence, and a future reader knows what evidence to look for.

Style note

Nothing enforces this, but every recent entry in TODO follows the same implicit template: what, then why or when. It is the same instinct that produced CONTEXT.md's Avoid lists and the ADR directory — write down the reasoning, not just the task, because the reasoning is what rots first.

Why git says “2 insertions, 1 deletion”

git diff --stat reports 1 file changed, 2 insertions(+), 1 deletion(-) for what is plainly the addition of a single line. This is not a mystery, but it trips people up often enough to be worth two paragraphs.

The TODO file has no trailing newline. You can see it in the raw bytes: the file ends …comments on PRs with no 0x0a after it. Git records that fact in the diff as the marker \ No newline at end of file, and the marker is attached to a specific line — the last one.

So when you append a line to such a file, two things change. The old last line gains a newline it did not have, and a new last line appears without one. In git's line-oriented model the old last line is therefore not unchanged: it must be deleted and re-added in its newline-terminated form. Hence one deletion and two insertions for one logical addition.

Edge case

The new line also ends without a newline, so the file's missing-trailing-newline quirk is preserved rather than fixed. Tidying it would have been defensible, but it would also have added a second unrelated line of churn to a commit whose entire virtue is being minimal. Leaving it alone is the right call — though it does mean the next person to append to TODO will see the same odd two-for-one diff.

The files that did not change

In a pull request this small, the absences are as informative as the presence. Four things a reader might reasonably have expected are all deliberately absent.

  • .github/workflows/explain-diff.yml is untouched. This is the whole point. The workflow must be frozen for the run to mean anything; had this pull request also tweaked it, it would have reproduced #59's confounding problem in miniature.
  • .github/workflows/explain-diff-cleanup.yml is untouched — and remains the one part of the lifecycle this run cannot exercise, since it fires only on closed.
  • No test was added. There is no meaningful unit test for "does a GitHub workflow deploy to a branch". The test is the run; the TODO line is the assertion, and a human eye is the test runner.
  • No GitHub Issue was filed, even though CLAUDE.md designates GitHub Issues as the tracker. The item went to TODO instead. That is consistent with how the file is already used — it holds small, self-assigned, near-term follow-ups — but it is worth naming as a judgement call rather than a rule. An argument exists for promoting this to an issue with a label, precisely because a one-line verification task is the kind of thing that quietly never gets done.

One further consequence of touching only TODO: the main ci.yml workflow still runs on this pull request, dutifully installing dependencies, linting, and executing the full pytest suite against a change to a text file. It will pass, and it tells you nothing. Only the explain-diff workflow is carrying information on this run.

Field notes from this run

Since the point of the exercise is to learn something about the pipeline, here are two things that surfaced while generating this page. Both are small, and both are exactly the sort of detail the TODO item was written to catch.

The prompt names a branch that does not exist locally. The workflow interpolates the base branch name and asks the agent to "compare the base branch master against the current branch head". But actions/checkout@v4 on a pull_request event leaves you on a detached merge ref with no local master branch. The obvious command fails:

$ git diff master...HEAD
fatal: ambiguous argument 'master...HEAD': unknown revision or path not in the working tree.

$ git rev-parse --verify master
fatal: Needed a single revision

$ git rev-parse --verify origin/master
2573a19a65739931a150dd88a077a80adf7eab33

The remote-tracking ref origin/master is present, so recovering is a matter of one extra step — but it is an extra step the agent has to discover, and it costs turns out of the --max-turns 40 budget. Saying origin/${{ ... base.ref }} in the prompt would remove the stumble entirely.

The checkout confirms the merge-ref semantics. HEAD here is 14cabdc, whose subject is literally "Merge ca6f860 into 2573a19". That is GitHub's synthetic merge commit, and it is why a workflow added inside a pull request does run within that same pull request. It also means the diff of interest is the two-dot range between the base commit and the head commit, not anything involving HEAD directly — a subtlety that a prompt phrased in terms of "branch head" glosses over.

Neither of these is a failure. The pipeline delivered its artefact. But they are precisely the friction you cannot see from reading YAML, and finding them is what a smoke test is for. The pull request that exists to test the pipeline has, in the course of being tested, produced two concrete suggestions for it.
