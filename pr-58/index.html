Reading your saved insights back: the /saved command

This is the fourth and final pull request in a short series that gives the Telegram language bot an explicit memory: a way for the user to keep something the bot said, and get it back later. The first three PRs built the storage and the write path — a SQLite table and a Save button. This one adds the read path: a single /saved command that lists everything the user has kept, plus an end-to-end test that proves the whole round trip survives a bot restart.

1. Background

The bot, from scratch

If you're new to this codebase, here's the shape of it. tg-language-assistant is a Telegram bot for people learning a second language. You send it a sentence, and it offers a row of buttons — Analyze, Correct, Rephrase, Reply — each of which asks an LLM to do something useful with what you wrote: explain a grammar point, fix your mistakes, suggest a more natural phrasing, or draft a reply you could send back.

Feel free to skip the rest of this subsection if you already know the bot's Trigger/Action architecture and just want the diff.

Vocabulary
A Trigger is a small class that handles one kind of Telegram event — a slash command, a text message, a button tap — and knows nothing about how the others work. A Conversation Turn is the unit the bot thinks in: the user's message (the anchor), plus whichever Action's result is currently rendered underneath it (the slot). Turns are addressed by slot_message_id, the Telegram message ID of the bot's reply.

Whatever the bot renders for an Action carries its own keyboard, built by build_action_keyboard() in bot/keyboard.py: the four action buttons, a Save button, and a thumbs-up/down row for feedback. Tapping any button fires a CallbackQueryHandler, which main.py routes to the right Trigger by matching the button's callback_data prefix.

Two more pieces matter for this change. UserSession wraps context.user_data — Telegram's per-user scratch space, which lives only as long as the process does — and tracks things like which language pair the user picked and which Action rendered which slot. And Localizer is the bot's translation layer: every user-facing string is a small class (a MsgKey) registered in bot/config/messages.py's catalog, and handlers call localizer.t(SomeMsgKey, locale) instead of writing English text inline. That's a project rule, not an accident — it means adding a second language later is a matter of filling in a new catalog dict, not hunting through every trigger for hardcoded strings.

The three PRs before this one

context.user_data is convenient but volatile: restart the bot process (a deploy, a crash, a routine redeploy) and every user's session — and with it, anything they thought they'd "kept" — is gone. The architecture decision record for this feature, ADR-0006, calls the fix explicit memory: a deliberate, durable "keep this" action, backed by real storage, independent of the ephemeral session. Three PRs led up to this one:

PR 1 — SQLite foundation

A Database wrapper and a migration runner, giving the bot a saved_insights table on a mounted volume.

PR 2 — SavedInsight & Repository

bot/insights.py: the SavedInsight dataclass, an InsightRepositoryProtocol, an in-memory fake for tests, and SqliteInsightRepository for production.

PR 3 — the Save button

A sixth row on the action keyboard and SaveTrigger, which turns a button tap into one INSERT — the write path.

Notice the shape of what got built: a write path that never touches the LLM and never depends on UserSession for the essentials, because — per ADR-0006 — a Save that silently fails because the session expired is far worse than a lost button tap elsewhere in the bot. Everything needed to reconstruct a SavedInsight is recovered straight off the Telegram callback: the anchor text from query.message.reply_to_message, the rendered result from query.message.text_html. Here's SaveTrigger.handle from PR 3, since this PR's trigger will mirror its style closely: 

async def handle(self, update: Update, context: ContextTypes.DEFAULT_TYPE) -> None:
    query = update.callback_query
    session = UserSession.from_context(context)
    slot_id = query.message.message_id
    ...
    insight = SavedInsight(
        user_id=update.effective_user.id,
        chat_id=query.message.chat.id,
        slot_message_id=slot_id,
        anchor_text=(getattr(anchor, "text", "") or "").strip(),
        ...
        action_type=session.get_slot_action(slot_id) or UNKNOWN_ACTION,
        result_text=query.message.text_html or query.message.text or "",
        parse_mode="HTML" if query.message.text_html else None,
        run_id=session.get_run_id(slot_id),
    )
    await self._repository.save(insight)
    await query.answer(t(MsgSaved, session.base_language))
    await query.edit_message_reply_markup(reply_markup=build_action_keyboard(saved=True))

So after three PRs, the bot could write a Saved Insight — but there was still no way for the user to see what they'd kept. Tap Save ten times over a week, and you'd have ten rows quietly accumulating in SQLite with absolutely no surface to view them. That's the gap this PR closes.

2. Intuition

The core idea of this PR is almost embarrassingly simple, which is exactly the point: the write path already stores everything needed for display, so the read path is just "fetch the rows and print them." No new tables, no new columns, no LLM call, no background job. One command, one query, one formatted reply.

Concretely: the user sends /saved. The bot looks up their Telegram user ID, asks the repository for their rows (most recent first — the repository already sorted them that way in PR 2), and if there are any, prints a numbered list. If there are none, it says so gently, with a nudge back toward the Save button.

●●●9:41🔋
Language Assistant
/saved
What you've kept:
1. Je suis allé au marché — correct, 2026-08-03
2. bonjour — analyze, 2026-08-01
Two things kept earlier this week, newest first. Each line names the original text, which button produced the result, and the date.
●●●9:41🔋
Language Assistant
/saved
Nothing kept yet. Tap 💾 Save on a reply to keep it for later.
A brand-new user, or one who's never tapped Save. The empty state is a nudge, not a dead end.

Here's the trick worth noticing: the trigger does no interpretation of its own. It doesn't re-run the Action, doesn't ask the LLM to summarize, doesn't reformat the stored HTML. It takes the plain fields already sitting in each SavedInsight row — anchor_text, action_type, created_at — and slots them into a template string. This is ADR-0006's "raw snapshot, distillation deferred" principle showing up concretely: the write path in PR 3 chose to store more than a minimal UI needs, precisely so that a read surface like this one could be built in an afternoon without touching the schema.

Worked example
Say the user's saved_insights table holds these two rows (trimmed to the columns this trigger actually reads):
idanchor_textaction_typecreated_at
1bonjouranalyze2026-08-01T10:02:00+00:00
2Je suis allé au marchécorrect2026-08-03T14:47:11+00:00
The repository's list_for_user returns them ordered created_at DESC, so row 2 comes first. The trigger enumerates them starting at 1 and formats each with MsgSavedListEntry: "{index}. {anchor} — {action}, {date}". The date is just the first ten characters of the ISO timestamp — a cheap way to get YYYY-MM-DD without pulling in a date-parsing dependency. Result: 
What you've kept:
1. Je suis allé au marché — correct, 2026-08-03
2. bonjour — analyze, 2026-08-01

One more piece of intuition, because it explains a design choice you'll see in the code: this reply is sent as plain text, with no parse_mode. Every other slot message in this bot is rendered as HTML — that's how bold corrections and inline diffs show up. But anchor_text is whatever the user originally typed, and result_text stored on the row can itself contain HTML the LLM produced. Stitching several of those into one list and asking Telegram to parse it as markup would be an easy way to accidentally break rendering — or worse, to let one saved insight's stray angle brackets corrupt how the rest of the list displays. Plain text sidesteps that entirely.

New UI strings

Following the project's rule that no user-facing text is ever hardcoded in a trigger, three new MsgKey subclasses go into bot/config/messages.py, alongside English entries in the catalog: 

class MsgSavedListHeader(MsgKey):
    pass

class MsgSavedListEmpty(MsgKey):
    pass

class MsgSavedListEntry(MsgKey):
    pass

# ...in CATALOGS["en"]:
MsgSavedListHeader: "What you've kept:",
MsgSavedListEmpty: (
    "Nothing kept yet. Tap 💾 Save on a reply to keep it for later."
),
MsgSavedListEntry: "{index}. {anchor} — {action}, {date}",

That last one is the interesting one: it's a template with placeholders, and Localizer.t() already supported **kwargs formatting (via Python's str.format) before this PR — it just hadn't been exercised with more than one placeholder yet. No changes were needed there; this PR is simply the first caller to lean on that capability.

The new file: SavedListTrigger

bot/triggers/saved_list.py is the heart of the PR. Structurally it's a sibling of SaveTrigger: a class with constructor-injected dependencies (the repository and the localizer — the project's house style is to inject collaborators rather than reach for module-level singletons or mock.patch) and a single async handle method. 

class SavedListTrigger:
    def __init__(
        self,
        repository: InsightRepositoryProtocol,
        localizer: Localizer,
    ) -> None:
        self._repository = repository
        self._localizer = localizer

    async def handle(self, update: Update, context: ContextTypes.DEFAULT_TYPE) -> None:
        session = UserSession.from_context(context)
        locale = session.base_language

        kept = await self._repository.list_for_user(user_id=update.effective_user.id)
        if not kept:
            await update.message.reply_text(self._localizer.t(MsgSavedListEmpty, locale))
            return

        lines = [self._localizer.t(MsgSavedListHeader, locale)]
        lines += [
            self._localizer.t(
                MsgSavedListEntry,
                locale,
                index=index,
                anchor=_shorten(insight.anchor_text),
                action=insight.action_type,
                date=_date_of(insight),
            )
            for index, insight in enumerate(kept, start=1)
        ]

        await update.message.reply_text("\n".join(lines))

Worth calling out explicitly, because it's easy to skim past:

  • Only update.effective_user.id feeds the query. There's no cross-user leakage risk here — the repository's SQL filters on WHERE user_id = ?, so one user can never see another's rows. The test suite added in this PR checks this directly (more below).
  • Session supplies only the display locale. Unlike SaveTrigger, which treats a missing session field as tolerable (falling back to UNKNOWN_ACTION, a null run_id), SavedListTrigger doesn't need session data to find the rows at all — the repository query is keyed entirely on the Telegram user ID, which is always available. Session here is a convenience for translation, not a dependency for correctness.
  • Two small free functions, _shorten and _date_of, handle presentation details: truncating a long anchor to 60 characters with an ellipsis so one long sentence can't push a list entry off screen, and slicing the first 10 characters off the ISO-8601 created_at string to get a plain date. Both are private to the module — not part of any interface, just formatting helpers.
Edge case
The comment directly above the final reply_text call spells out why there's no parse_mode="HTML" here, even though most of the bot's replies use it: "entries carry user-supplied anchor text and LLM output, neither of which is safe to hand to Telegram as markup." If a saved anchor happened to contain something that looked like an unclosed HTML tag, Telegram's HTML parser would reject the whole message. Plain text can't be broken that way.

Wiring it into main.py

bot/main.py gets a small, mechanical addition: the new trigger is constructed and registered exactly the way every other trigger is. 

insight_repository = SqliteInsightRepository(database=database)
save_trigger = SaveTrigger(repository=insight_repository)
saved_list_trigger = SavedListTrigger(
    repository=insight_repository, localizer=localizer
)

app.add_handler(CommandHandler("start", settings_trigger.handle))
app.add_handler(CommandHandler("settings", settings_trigger.handle))
app.add_handler(CommandHandler("saved", saved_list_trigger.handle))

The only thing to notice is that SqliteInsightRepository(database=database) used to be constructed inline as an argument to SaveTrigger; it's now pulled out into an insight_repository local so that both triggers can share the same instance. Since SqliteInsightRepository is a thin, stateless wrapper around a shared Database connection, this is purely a wiring convenience, not a behavior change — a fresh instance would have worked identically.

The tests

Two test files land with this PR, at different altitudes.

bot/triggers/test_saved_list.py is a unit-level suite for SavedListTrigger alone, using the in-memory fake repository from PR 2 (InMemoryInsightRepository) rather than real SQLite — fast, and focused purely on the trigger's own logic:

TestWhat it pins down
test_lists_kept_insights_most_recent_first Ordering is newest-first end to end, not just at the repository layer.
test_shows_which_action_produced_each_insight The action type (analyze, correct, ...) actually shows up in the reply text.
test_says_so_when_nothing_has_been_kept The empty state matches MsgSavedListEmpty exactly, with no header prepended.
test_lists_only_the_requesting_users_insights User isolation — someone else's saved insight never appears in your list.

tests/test_explicit_memory.py sits at a different altitude entirely — it's the acceptance test for the whole four-PR feature, and it's the reason this PR is titled "Add /saved and an end-to-end restart test." Rather than mocking anything, it drives SaveTrigger and SavedListTrigger against a real SQLite file on disk, with a deliberate break in the middle: 

async def test_a_kept_turn_survives_a_bot_restart(tmp_path):
    db_path = tmp_path / "bot.db"

    # First run — the user deep-dives a message and keeps the result.
    database = Database(path=db_path)
    await database.connect()
    save = SaveTrigger(repository=SqliteInsightRepository(database=database))
    tap = make_callback_update(
        callback_data=SAVE, message_id=77,
        reply_text="Je suis allé au marché",
        slot_text="'allé' agrees with the subject",
    )
    tap.callback_query.message.reply_markup = build_action_keyboard()
    await save.handle(tap, make_context(user_data={"slot_actions": {77: "correct"}}))
    await database.close()

    # Restart — a brand-new connection and an empty Session, as after a deploy.
    database = Database(path=db_path)
    await database.connect()
    saved_list = SavedListTrigger(
        repository=SqliteInsightRepository(database=database), localizer=Localizer()
    )
    request = make_update()
    await saved_list.handle(request, make_context())
    await database.close()

    listed = request.message.reply_text.call_args.args[0]
    assert "Je suis allé au marché" in listed
    assert "correct" in listed

The comments in the test spell out exactly what's being simulated: the second block opens a brand-new Database connection and a brand-new, empty context.user_data — that's what actually happens across a real deploy, where the process (and every in-memory UserSession) is gone, but the SQLite file on the mounted volume persists. If this test passes, it's real evidence — not just an inference from unit tests — that the memory is explicit in the sense ADR-0006 intended: durable independent of any particular running process.

Why this test matters more than it looks
Nothing before this PR actually exercised the full loop. PR 2's tests covered the repository against real SQLite; PR 3's tests covered SaveTrigger with an in-memory fake. This is the first test that writes via one Trigger, closes the database, reopens it, and reads via a different Trigger — which is the only way to catch, say, a repository whose columns don't round-trip cleanly through SQLite, or a Save that only appeared to work because the in-memory fake was forgiving about something the real database is not.
