1Background

1.1 How this project keeps its two brains in sync

Every non-trivial codebase accumulates two kinds of knowledge. There is the code itself — precise, executable, and forever up to date because it has to be, or nothing runs. And there is the vocabulary the team uses to talk about the code: the names for the concepts, the reasons certain designs were chosen over others, the boundaries between one module's job and the next one's. That second kind of knowledge is just as real, but nothing forces it to stay accurate. It lives in people's heads, in old Slack threads, in the memory of whoever wrote the original pull request — and it decays the moment that person moves on to something else.

This repository fights that decay with two files that skip if you're already familiar with the pattern: CONTEXT.md at the repo root, and a numbered sequence of decision records under docs/adr/. CONTEXT.md is a living glossary — it defines every domain term the codebase uses ("Anchor Message", "Slot Message", "Action Runner", and so on) in one place, so that when someone writes a docstring or names a variable, there's a single source of truth for what that word is supposed to mean. Each entry can also carry an _Avoid_ line: near-synonyms that are deliberately rejected, so that "message handler" and "callback handler" don't both creep in for the same concept over time.

The ADR folder complements this by recording why, not just what. An ADR is a short, permanent note: here's the decision, here are the options we considered and rejected, here are the consequences we accepted going in. Once written, an ADR is not usually edited to reflect new decisions — a change of mind gets a new ADR that supersedes the old one. That way the history of "why is it built this way?" stays intact even as the answer evolves.

Why this matters for this PR The change you're about to read touches neither of these files' surrounding application code. It is a pure edit to the glossary and a pure addition to the ADR log. Nothing runs differently after this PR merges — but the vocabulary the team will use to build the next four PRs on top of it has just been locked in.

1.2 Where "Save" stood before this change

To see what changed, it helps to know what the glossary said before. Scattered through CONTEXT.md, a few entries described a feature that had been designed in prose but never built in code — there is, today, no Save button and no persistence layer for it anywhere in bot/. The glossary described the intended shape of a not-yet-existing feature, and that description is exactly what this PR revises.

Before this PR

Vocabulary List — "A per-user persistent collection of vocabulary entries built two ways: passively (extracted automatically from Vocabulary Hint / Analyze) and actively (user taps Save, which saves the anchor message and its translation as an entry)."

Vocabulary Repository — "The future persistence module for Vocabulary Lists. Deferred until after core architecture is stable."

After this PR

Saved Insight — an immutable, verbatim snapshot of a whole Conversation Turn, captured the instant the user taps Save.

Vocabulary List — a derived view, recomputed by scanning Saved Insights. It has no write path or repository of its own; the "Vocabulary Repository" term is retired.

Notice the word "entry" in the old definition. It quietly implied that tapping Save produces something small and translation-shaped — a word, a phrase, a flashcard. That's a reasonable first guess for a language-learning bot, but it collapses two different things into one: the raw material captured at the moment of saving, and the vocabulary-card view a user might eventually want to browse. This PR's job is to pull those two things apart before either gets built.

2Intuition

2.1 The core shift: a turn, not a word

Picture a learner mid-conversation. A native-speaking friend sends them a message in French; the bot's default Instant Action translates it; the learner then taps the Correct button on their own reply-in-progress and gets back an annotated correction. That whole exchange — the original message, which Action ran, and the formatted result — is one Conversation Turn, already a defined concept in this glossary before this PR.

Under the old wording, tapping Save on that turn would produce a "vocabulary entry" — as if the only thing worth keeping was a word pair. But a Correct result isn't a word pair, it's a whole annotated sentence. A Reply suggestion isn't a word pair either. The old definition was implicitly written with only the Translate and Vocabulary Hint actions in mind, and quietly broke down for everything else the bot can do.

This PR's core move is to rename and re-scope what gets captured: it's not a vocabulary entry, it's a Saved Insight — the entire turn, saved exactly as it was displayed, regardless of which Action produced it.

Comment dit-on "I'm running late" en français ?
Correct result:
"Je suis en retard" — use "en retard", not "tard", for punctuality
Analyze Reply 💾 Save

Tapping Save here keeps the whole Correct result — not a word extracted from it.

The Vocabulary List doesn't disappear from the glossary — it's simply redefined as something computed from Saved Insights, on read, rather than something written to directly. If the learner later wants to review vocabulary, that view scans through their Vocabulary Hint and Analyze Saved Insights and lifts the words back out of them. The Correct-result example above wouldn't feed into that particular view (it isn't a Vocabulary Hint or Analyze result) — and that's fine, because the Vocabulary List was never meant to be the only lens onto a user's Saved Insights, just one read-side interpretation of them.

Saved Insight is the single write path. Vocabulary List is one possible read, not built yet, with no storage of its own.

2.2 Why raw snapshots, not distilled cards

Once you decide to capture the whole turn, a design question follows immediately: capture it as-is, or run it through another LLM call first to produce something tidier — a title, an extracted vocabulary pair, a one-line summary? ADR-0006 answers this directly, and the reasoning is worth sitting with because it will shape everything built on top of the Insight Repository later.

The argument is about which direction is reversible. If you store the raw turn — the anchor text, the Action type, the rendered HTML result, the Language Pair in force — you can always run a distillation over it later: extract vocabulary, generate a title, cluster related saves, whatever a future feature needs. But if you distil first and only keep the distilled card, whatever the distillation prompt didn't think to keep is gone. There's no way to recover the original Correct annotation from a card that only kept "en retard → running late".

Key decision Write raw, distil later. A raw snapshot can always be turned into any future view. A distilled snapshot can never be turned back into the raw material it discarded.

There's a second, more practical reason tucked into the ADR: an LLM call on the write path makes the Save tap slow and fallible. For a bot whose stated core value is speed — the primary user is mid-conversation with a real person, waiting — a Save button that can spin or time out is worse than not having a distilled card yet. So the write path does no LLM call and no interpretation at all; it's a straight copy of what's already on screen into a database row.

2.3 Append-only, and independent of Session

Two more properties round out the design, and both trace back to the same instinct: a Save should never silently fail, and it should never silently overwrite something the user chose to keep.

Append-only. If the learner runs Correct on a turn, saves it, then later goes back to the same turn and runs Analyze instead, saving again doesn't overwrite the first save — it creates a second Saved Insight. The glossary entry gives this a precise mechanism: a natural key of (user_id, chat_id, slot_message_id, action_type). Re-tapping Save on the exact same rendered result is a no-op (same key, nothing new to add), but a different Action on the same turn is a genuinely new row.

user_idchat_idslot_message_idaction_typeResult
421001887correctNew row — first save of this turn+action
421001887correctNo-op — identical key already saved
421001887analyzeNew row — different Action, same turn

Independent of Session. This is the subtler of the two, and it's where the ADR draws an explicit contrast with two features that already exist in the codebase: Suggestion selection and Rating. Both of those depend on the in-memory Session (a per-user dictionary held in context.user_data) to know what to do when a button is tapped — and both are designed to silently no-op if that Session state has been lost, for instance after a bot restart. That's an accepted trade-off for those two features, because the cost of failure is small: one lost tap, no data corruption, nothing the user was told succeeded.

A lost Save is a different kind of failure. The user believes they've kept something, permanently, for later. So the capture path is deliberately built to not depend on Session at all — everything it needs travels on the Telegram callback itself.

Suggestion / Rating

anchor = slot_message.reply_to_message result_text = slot_message text run_id = Session, but nullable
Same "Session might be gone" risk, two different responses — because the cost of failure differs.

The one piece of Session-derived data a Saved Insight would ideally carry — the run_id that links back to a LangSmith Trace — is nullable for exactly this reason. If it's there, great, the Saved Insight can be traced back to the LLM call that produced it. If Session was lost and it isn't there, the Save still happens; you just lose the trace link, not the insight itself.

3Code Walkthrough

With the intuition in place, the diff itself is short and reads almost like a specification. It touches exactly two files: an edit to CONTEXT.md and a new docs/adr/0006-saved-insights-capture-raw-turns.md. No application code changes — this is the "PR 0 of 4" in a four-part rollout, the part where the team agrees on words before writing the persistence layer, the callback handler, and the /saved command that will follow.

3.1 Two new glossary entries

The diff adds Saved Insight and Insight Repository as fresh entries in the Ubiquitous Language section: 

### Saved Insight
An immutable snapshot of one Conversation Turn that the user explicitly chose
to keep. Captures the Anchor Message, the Action that produced the result,
the rendered result text, and the Language Pair in force at the time.
Written verbatim — no LLM call and no interpretation on the write path...
Append-only: saving the same turn again after running a different Action
produces a second Saved Insight, not an edit. Capture never depends on
Session... Surfaced via `/saved`.
_Avoid_: note, bookmark, memory, favourite, card

### Insight Repository
The module that owns persistence of Saved Insights. Follows the repository
abstraction established in ADR-0001 (SQLite backend, swappable interface).
Append-only from the caller's perspective... Deletion is represented as a
soft delete, never a row removal.
_Avoid_: insight store, memory store

Two things are worth calling out about how these entries are written. First, Insight Repository is defined by reference to ADR-0001 rather than re-litigating storage — it explicitly reuses the SQLite-behind-an-interface pattern the project already committed to for User Preferences. Second, the _Avoid_ list on Saved Insight is doing real work: "memory" is banned specifically because it would collide with the unrelated LLM sense of conversational memory — this bot deliberately keeps no multi-turn LLM state, so reusing that word here would be actively misleading to a future reader.

3.2 Vocabulary List, redefined as a view

The existing Vocabulary List entry is rewritten in place, and the Vocabulary Repository entry — which described a not-yet-built persistence module — is deleted outright: 

### Vocabulary List
A per-user persistent collection of vocabulary entries built two ways:
passively (words/phrases automatically extracted from Vocabulary Hint and
Analyze actions) and actively (user taps the Save button in the inline
keyboard, which saves the anchor message and its translation as an entry).
Passive and active entries are distinguished in the list. Accessible via
/history. Active entries are surfaced separately as "Favourites."
A per-user view of the vocabulary a user has encountered — words and
phrases lifted from the stored results of their Vocabulary Hint and Analyze
Saved Insights. A derived view, not a store: it has no capture path of its
own and is recomputed from Saved Insights rather than written to. Not yet
built.

### Vocabulary Repository
The future persistence module for Vocabulary Lists. Deferred until after
core architecture is stable — the Vocabulary List exists as a domain
concept but is not yet persisted across restarts.

This is the sharpest edit in the whole PR. The old text described a "passive vs. active" distinction, a /history command, and a "Favourites" sub-view — a fairly detailed feature spec for something that had never been built. All of it is deleted, replaced by one honest sentence: this is a read computed from Saved Insights, and it doesn't exist yet. The Vocabulary Repository entry, which would have owned a storage table that now has no reason to exist (there's nothing to persist beyond what the Insight Repository already persists), is removed rather than reworded, because there is no future module left to describe.

3.3 Relationships and flagged ambiguities

The PR also introduces two new sections to CONTEXT.md that didn't exist before at all: Relationships, a short list of cardinality facts connecting the new terms — 

## Relationships

- A Conversation Turn may produce zero or more Saved Insights — one per
  Action whose result the user chose to keep
- A Saved Insight belongs to exactly one Conversation Turn and records
  exactly one Action
- A Saved Insight carries the Language Pair in force when it was saved,
  not the user's current one
- The Insight Repository is the sole read/write interface for Saved
  Insights
- The Vocabulary List is derived from Saved Insights; it is never
  written to directly

— and Flagged ambiguities, which does something glossaries rarely do explicitly: it names the confusion this PR is resolving, in plain language, so a future reader doesn't have to reconstruct it from a git blame. 

## Flagged ambiguities

- "Save" previously meant adding an entry to the Vocabulary List. It now
  means capturing a Saved Insight — a whole turn, not a word. The
  Vocabulary List keeps its name but is now a derived view over Saved
  Insights, with no capture path of its own; the "Vocabulary Repository"
  term is retired as a result.
- "Memory" was used informally for this capability while it was being
  designed. Resolved: the domain term is Saved Insight. "Memory" is
  avoided because it collides with the LLM sense of conversational
  memory, which this bot deliberately does not keep (see LLM Interface
  — no multi-turn state).
Why write down the ambiguity at all? Anyone reading this repo's history — including whoever picks up parts 1 through 4 of this feature — will likely have "Save = vocabulary entry" as their starting mental model, since that was the wording for a while. Recording the correction here, instead of letting it live only in a PR description, means the glossary itself carries the "don't be confused by the old meaning" warning forward.

3.4 ADR-0006: capture raw turns

The new decision record lays out the reasoning already covered in the Intuition section above, in the project's standard ADR shape: a title framed as the decision itself, the options considered, and the consequences accepted. Two parts of the "Consequences" section are worth reading closely because they pin down details that aren't obvious from the glossary text alone: 

- Append-only. Re-saving a turn after running a different Action creates
  a second row; the natural key is (user_id, chat_id, slot_message_id,
  action_type), so re-tapping the same view is a no-op.

- Capture never depends on Session. Everything needed is carried on the
  Telegram callback — the anchor is recovered from the slot message's
  reply_to_message, the result text from the message itself. Only run_id
  comes from Session, and it is nullable. This is a deliberate departure
  from Suggestion selection and Rating, which silently no-op when Session
  is lost...

- Rendered text is stored with its parse_mode. The stored result is
  presentation-coupled HTML, not a normalized structure... a Saved
  Insight can always be re-displayed exactly as it was first seen,
  without re-running the Action's formatter.

- Deletion is soft. A deleted_at column exists from the first migration
  so that removal never violates append-only, even though no delete UI
  ships initially.

That third point is a small but consequential implementation detail: because the bot already carries a parse_mode per Action (HTML or plain text, an existing concept defined under Action in the glossary), storing the result alongside its parse_mode means a future /saved command can hand the stored text straight back to Telegram's send_message call unmodified — no re-running the formatter, no risk of the redisplayed version drifting from what the user originally saw.

The fourth point — soft delete via a deleted_at column baked into the very first migration — is a case of designing the schema for a feature (deletion) before building its UI. It costs one nullable column now, and it means that whenever a delete button does ship, it never has to violate the append-only guarantee by physically removing a row a user once chose to keep.
