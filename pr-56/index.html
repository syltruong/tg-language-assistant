Background

What this bot does, for newcomers

Skip this bit if you already know the bot. The project is a Telegram bot that sits next to a language learner mid-conversation. The learner is chatting with a native speaker in, say, French, and doesn't quite understand a sentence, or wants help composing a reply. They forward the message to the bot (that's called the Anchor Message) and the bot writes back with a translation, a correction, or a set of reply suggestions — whichever Action the situation calls for.

Everything the bot says about one Anchor Message lives in a single message, the Slot Message, which carries an inline keyboard of buttons: Analyze, Correct, Reply, and so on. Tapping a button doesn't post a new message — it edits the Slot Message in place. The whole unit of interaction, from the Anchor Message through however many keyboard taps the user makes, is called a Conversation Turn.

Je suis allé au marché hier.
"I went to the market yesterday." — a simple past-tense sentence.
One Conversation Turn: the anchor message on the right, the Slot Message (with its keyboard) on the left. Tapping Save is what this PR's code makes durable.

Until now, whatever the bot showed the user was ephemeral — it lived in the chat history, and in an in-memory Session object that evaporates on restart. This PR is part of a small arc of work (branch name: explicit-memory) that gives the user a way to explicitly keep a result forever: the Saved Insight. It's an immutable snapshot of one Conversation Turn's outcome, and it's the foundation for a future /saved command and a vocabulary review feature.

The repository pattern already in place

One protocol, one fake for tests, one real implementation talking to an external system — all three defined together in a single file. This diff follows exactly that shape for SavedInsight, just with SQLite instead of LangSmith as the "real" backend.

The SQLite foundation this PR builds on

The base branch this diff is compared against — claude/explicit-memory-sqlite — already contains PR 0 and PR 1: the domain-language write-up, and a small Database class (bot/storage/db.py) that opens a single SQLite file and brings its schema up to date using PRAGMA user_version as a version counter, applying any bot/storage/migrations/*.sql file numbered higher than the current version.

The first migration, 0001_saved_insights.sql, already creates the table this PR's code reads and writes:

In other words: by the time this diff starts, the table exists and the connection machinery exists. What's missing — and what this PR adds — is the Python-side object that turns a SavedInsight value into a row in that table, and back again.

Intuition

The core idea of this PR is small enough to say in one sentence: a SavedInsight is a plain data value, and an InsightRepositoryProtocol is the only door through which it enters or leaves storage — with two interchangeable rooms behind that door, one real (SQLite) and one fake (an in-memory list), so that every other part of the bot can be tested without touching a database file.

User taps Save on the Slot Message
↓

from the callback data
↓
calls repository.save(insight)
— an InsightRepositoryProtocol
↓
InMemoryInsightRepository

The Trigger that will call this code (arriving in PR 3) never needs to know which implementation it's holding — only that it satisfies the protocol.

Concretely, imagine the user runs Analyze on the French sentence "bonjour" and taps Save. The trigger (not part of this diff yet) will construct something like: 

SavedInsight(
    user_id=1, chat_id=2, slot_message_id=3,
    anchor_text="bonjour", detected_language="fr",
    base_language="en", target_language="fr",
    action_type="analyze", result_text="a casual greeting",
)

and hand it to repository.save(...). Whether that repository is the in-memory fake or the real SQLite one, the same thing happens: the value is stamped with an id and a created_at, and stored.

Idempotent by construction, not by an if statement

ADR-0006 (already agreed before this PR) says re-tapping Save on the same view should be a no-op, not a duplicate row. This diff implements that not with application-level "have I seen this before?" logic, but by leaning on the database's own UNIQUE constraint on (user_id, chat_id, slot_message_id, action_type) — the four columns that together identify "this particular result, for this particular turn". The in-memory fake mirrors the same rule in plain Python so that it behaves identically in tests.

1st tap: save(user=1, chat=2, slot=3, action="analyze")
↓
Row inserted. Returns id = 7
↓
2nd tap: save(user=1, chat=2, slot=3, action="analyze")
↓
UNIQUE constraint violated. Caught. Returns None — no second row.
Double-tapping Save on the same slot message and the same action is silently absorbed. Running Correct on the same turn afterwards is a different action_type, so it inserts a second, separate row.
Why no LLM call here
ADR-0006, already decided before this code was written, insists the write path is verbatim: no distillation, no LLM call, nothing that could time out or fail. That's why save() and list_for_user() are the entire surface area — there's no "generate a title" step to see in this diff, because that's explicitly a read-side concern for later.

Code walkthrough

The whole diff is two new files: bot/insights.py (143 lines) and its test suite bot/test_insights.py (157 lines). Nothing else changes — no existing file is touched, no migration is added (that already happened in PR 1). Let's go through bot/insights.py top to bottom.

The SavedInsight dataclass

bot/insights.py 
@dataclass(frozen=True, slots=True)
class SavedInsight:
    user_id: int
    chat_id: int
    slot_message_id: int
    anchor_text: str
    detected_language: str
    base_language: str
    target_language: str
    action_type: str
    result_text: str
    parse_mode: str | None = None
    run_id: str | None = None
    created_at: str | None = None
    id: int | None = None

This is a plain, frozen value object — it carries no behaviour and knows nothing about SQL or Telegram. Notice the split between required fields (everything the caller must supply about the turn) and the three fields that default to None: parse_mode and run_id are genuinely optional (a Saved Insight can exist without a LangSmith trace behind it), while id and created_at are assigned by the repository — a caller constructs a SavedInsight without them and gets one back with them filled in from save()'s return value (or, in this repo's case, from a subsequent list_for_user() read).

frozen=True means the dataclass is immutable — matching the domain rule that a Saved Insight, once written, is never edited. Making a stamped copy (with an id and timestamp) uses dataclasses.replace rather than mutation, which you'll see in the in-memory fake below.

The protocol

bot/insights.py 
@runtime_checkable
class InsightRepositoryProtocol(Protocol):
    async def save(self, insight: SavedInsight) -> int | None:
        """Store an insight. Returns its id, or None if this turn+action is already kept."""
        ...

    async def list_for_user(
        self, user_id: int, limit: int = _DEFAULT_LIMIT
    ) -> list[SavedInsight]: ...

Two methods, both async (the whole bot is built on asyncio, and aiosqlite is the async SQLite driver in use elsewhere in the project). save's return type, int | None, directly encodes the idempotency rule from the intuition section: a fresh save returns the new row's id, a duplicate returns None. Anything downstream (a future trigger) can use that to decide whether to show "Saved!" or "Already saved" feedback, without needing to catch an exception itself.

The in-memory fake

bot/insights.py 
class InMemoryInsightRepository:
    """Fake for tests and local development."""

    def __init__(self) -> None:
        self._insights: list[SavedInsight] = []
        self._next_id = 1

    async def save(self, insight: SavedInsight) -> int | None:
        if any(_turn_key(stored) == _turn_key(insight) for stored in self._insights):
            return None

        stored = replace(insight, id=self._next_id, created_at=_now())
        self._insights.append(stored)
        self._next_id += 1
        return stored.id

    async def list_for_user(
        self, user_id: int, limit: int = _DEFAULT_LIMIT
    ) -> list[SavedInsight]:
        matching = [i for i in self._insights if i.user_id == user_id]
        return sorted(matching, key=lambda i: i.id, reverse=True)[:limit]

This is a genuine fake, not a mock — a real (if simplified) working implementation backed by a Python list, matching the codebase's stated preference for fakes-behind-a-protocol over mock.patch. It duplicates the uniqueness rule by hand via a small helper, _turn_key, defined near the bottom of the file: 

def _turn_key(insight: SavedInsight) -> tuple[int, int, int, str]:
    """The natural key mirroring the table's UNIQUE constraint."""
    return (insight.user_id, insight.chat_id, insight.slot_message_id, insight.action_type)

That comment is important, and worth calling out: the tuple (user_id, chat_id, slot_message_id, action_type) here has to stay in lockstep with the UNIQUE (...) clause in the SQL migration from PR 1. They're two independent expressions of the same business rule, in two different implementations — a small but real maintenance hazard if one is ever changed without the other, since nothing enforces they stay in sync except this comment and the shared test suite (more on that below).

The SQLite implementation

bot/insights.py 
class SqliteInsightRepository:
    def __init__(self, database: Database) -> None:
        self._database = database

    async def save(self, insight: SavedInsight) -> int | None:
        try:
            cursor = await self._database.connection.execute(
                f"""
                INSERT INTO saved_insights ({_COLUMNS})
                VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?, ?)
                """,
                (insight.user_id, insight.chat_id, ... , _now()),
            )
        except aiosqlite.IntegrityError:
            # The UNIQUE constraint — this turn and action are already kept.
            return None

        await self._database.connection.commit()
        return cursor.lastrowid

This is where the idempotency intuition becomes concrete: rather than querying "does this already exist?" before inserting (a check-then-act that would race under concurrent taps), the code just attempts the insert and catches aiosqlite.IntegrityError if the database's own UNIQUE constraint rejects it. The database is the single source of truth for "has this been saved already", which is a nice illustration of pushing an invariant down to the layer that can actually enforce it atomically.

The class takes a Database (from bot/storage/db.py, PR 1) via constructor injection — again, no reaching out to a global connection or module-level function. Column names are centralised in a module-level constant so the INSERT and SELECT statements can't silently drift apart: 

_COLUMNS = """
    user_id, chat_id, slot_message_id, anchor_text, detected_language,
    base_language, target_language, action_type, result_text, parse_mode,
    run_id, created_at
"""

Reading back is a straightforward SELECT, scoped to one user, filtered to exclude soft-deleted rows, and converted row-by-row back into SavedInsight values: 

async def list_for_user(
    self, user_id: int, limit: int = _DEFAULT_LIMIT
) -> list[SavedInsight]:
    cursor = await self._database.connection.execute(
        f"""
        SELECT id, {_COLUMNS} FROM saved_insights
        WHERE user_id = ? AND deleted_at IS NULL
        ORDER BY created_at DESC, id DESC
        LIMIT ?
        """,
        (user_id, limit),
    )
    return [_from_row(row) for row in await cursor.fetchall()]

def _from_row(row: aiosqlite.Row) -> SavedInsight:
    return SavedInsight(**dict(row))

Two small things are worth noticing here. First, ordering is created_at DESC, id DESC rather than just created_at — a tie-breaker on id guards against two saves landing in the same timestamp (ISO strings from datetime.now(UTC) have microsecond resolution, but ties are still cheap insurance). Second, _from_row works because Database.connect() (in PR 1) sets connection.row_factory = aiosqlite.Row, which makes each row behave like a mapping — dict(row) turns it directly into the dataclass's keyword arguments. That only works because the SELECT's column list, order aside, matches the dataclass fields by name; the deleted_at column itself is deliberately not selected, since SavedInsight has no field for it — soft-deletion is a storage-layer concern the domain object doesn't need to know about.

The shared test suite

The most structurally interesting part of bot/test_insights.py is not any individual test, but the fixture that parametrizes every test in the file over both implementations:

bot/test_insights.py 
@pytest.fixture(params=["sqlite", "in_memory"])
async def repository(request, tmp_path):
    if request.param == "in_memory":
        yield InMemoryInsightRepository()
        return

    database = Database(path=tmp_path / "bot.db")
    await database.connect()
    yield SqliteInsightRepository(database=database)
    await database.close()

Every test that asks for the repository fixture — saving, idempotency, listing, ordering, user-scoping, round-tripping every field — runs twice, once per backend. That's the payoff of the protocol-plus-fake pattern: it's not just that the fake makes other modules' tests fast and dependency-free (the trigger tests that PR 3 will add), it's that this file's own module docstring says so explicitly —

from the module docstring
"Every test runs against both implementations. The fake is what PR 3's trigger tests depend on, so it has to behave like the real one or those tests lie."

That's the guard against the "two implementations of the same uniqueness rule" hazard mentioned earlier: if someone changes the SQL migration's UNIQUE clause without updating _turn_key, the test_keeping_the_same_turn_and_action_twice_stores_one_insight test (or its siblings) will fail for one parametrization and pass for the other, immediately surfacing the drift.

A couple of individual tests are worth calling out for what they lock in about behaviour that isn't obvious from the schema alone: 

async def test_a_run_id_is_optional(self, repository):
    """Session may be gone by the time Save is tapped — capture must not depend on it."""
    await repository.save(an_insight(run_id=None))

    kept = (await repository.list_for_user(user_id=1))[0]

    assert kept.run_id is None

This directly encodes an ADR-0006 consequence: unlike other features in this bot, capturing a Saved Insight must not silently fail just because the in-memory Session has been lost (say, after a bot restart). And the last class in the file, TestSoftDeletion, exercises a code path with no UI yet — it reaches directly into the database to set deleted_at and confirms list_for_user honours it — a deliberate "the plumbing works even though nothing calls it yet" test, consistent with the schema shipping the column ahead of any delete button.
